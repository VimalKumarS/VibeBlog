ShipIt — a containerised microservice platform

Throughout this guide we'll containerise ShipIt: an API server, a worker process, a Redis cache, and a PostgreSQL database — going from bare code to a production-ready multi-container stack with networking, volumes, health checks, and security hardening.

Chapter 1

The problem Docker
solves.

Before Docker: "It works on my machine." After Docker: the machine is part of the artifact. You ship not just code but the exact filesystem, libraries, runtime, and configuration the code needs to run.

The core insight: applications need their environment. A Python 3.11 app needs Python 3.11, its pip packages, its config files, its system libraries. Docker packages all of that into an image — a single, portable, immutable artifact that runs identically on a developer laptop, a CI runner, and a production server.

before vs after docker — click to compare showing: without docker

VM: heavyweight isolation

  • Full OS per workload — gigabytes of overhead.
  • Boots in minutes. Slow to provision and scale.
  • Hypervisor virtualises hardware — duplicates the kernel.
  • Ports between host and guest are configured explicitly.
  • Image sizes: 2–20 GB. Long push/pull cycles.

Container: lightweight isolation

  • Shares host OS kernel — no duplicate kernel.
  • Starts in milliseconds. Ephemeral by design.
  • Isolation via kernel namespaces and cgroups.
  • Image sizes: 5 MB (alpine) – 1 GB. Fast.
  • Reproducible: same image = same behaviour everywhere.
Container = namespaces + cgroups + union filesystem
Namespaces — isolate: PID tree, network interfaces, mounts, users, hostname, IPC. The container thinks it's alone.
cgroups — limit: CPU cores, memory, disk I/O, network bandwidth. The container can't consume more than its allocation.
Union filesystem — layers: image layers stacked read-only, thin writable layer on top. Containers share image layers → fast startup, small disk footprint.
Chapter 2

Docker architecture —
daemon, client, registry.

Docker is a client-server system. The CLI you type commands into is just a client — it sends API calls to the Docker daemon (dockerd), which does all the real work: building images, starting containers, managing networks.

docker architecture — animated request flow idle
💻

Docker CLI

Sends REST API requests to the Docker daemon via a Unix socket (/var/run/docker.sock) or TCP. Thin client — no logic, just API calls.

⚙️

dockerd

The daemon. Manages images, containers, networks, volumes. Delegates container runtime to containerd. Listens on unix:///var/run/docker.sock.

🔧

containerd

Industry-standard container runtime. Handles image pulls, storage, container lifecycle. Used directly by Kubernetes too. OCI compliant.

🏃

runc

Low-level OCI runtime. Actually creates the container: sets up namespaces, cgroups, mounts the filesystem, executes the process. Called by containerd.

🏪

Registry

Image storage server. Docker Hub (public), ECR, GCR, ACR (cloud), Harbor (self-hosted). Images pushed/pulled via HTTPS. Content-addressed by digest.

🔨

BuildKit

Next-gen image builder. Parallel layer building, cache mounts, secret injection, cross-platform builds. Default since Docker 23. Massive build speed improvements.

Chapter 3

Images and
layers — the
union filesystem.

A Docker image is a stack of read-only layers. Each Dockerfile instruction creates a new layer. When a container starts, a thin writable layer is added on top. This is what makes containers fast, small, and shareable.

image layer build — watch each Dockerfile instruction create a layer step 1 of 6

ShipIt API server — optimised Dockerfile

# Stage 1: build dependencies (cached aggressively) FROM python:3.11-slim AS builder WORKDIR /app # Copy ONLY requirements first — layer cached unless requirements change COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt # Stage 2: production image — no build tools FROM python:3.11-slim WORKDIR /app # Copy installed packages from builder stage COPY --from=builder /usr/local/lib/python3.11/site-packages /usr/local/lib/python3.11/site-packages COPY --from=builder /usr/local/bin /usr/local/bin # Copy application code LAST (changes most frequently) COPY src/ ./src/ # Security: non-root user RUN useradd -m -u 1001 appuser USER appuser EXPOSE 8080 CMD ["python", "-m", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8080"]
layer caching — how build cache works across rebuilds first build
Cache invalidation rule: if a layer changes, ALL subsequent layers are invalidated. This is why you copy requirements.txt before copying source code — requirements change rarely, source code changes constantly.
Multi-stage builds eliminate build tools from the final image. Your final image contains no compiler, no pip cache, no test dependencies — only what the running app needs. ShipIt goes from 800 MB (single stage) to 120 MB (multi-stage).

Containers —
isolation by kernel.

A container is not a VM. It's a process (or group of processes) on the host, isolated by Linux kernel features: namespaces give it the illusion of being alone, cgroups limit what it can consume.

Chapter 5

Container
networking —
four modes.

Docker creates virtual network interfaces for containers. By default, containers on the same network can reach each other by name. Traffic between containers never leaves the host. Understanding network modes is essential for multi-container applications.

network mode visualisation bridge

User-defined bridge networks

  • Containers communicate by container name as hostname — no IP needed.
  • shipit-api reaches redis at redis:6379 — that's it.
  • Better than default bridge: DNS-based service discovery built in.
  • Containers on different user-defined networks are isolated by default.

Port mapping

  • -p 8080:8080 → host:8080 → container:8080.
  • -p 127.0.0.1:5432:5432 → bind to loopback only (security).
  • Ports only published to the host — container-to-container traffic uses internal IPs, no host port needed.
  • iptables DNAT rules created automatically by dockerd.
dns resolution — how shipit-api finds redis by name resolving…
# Create isolated network for ShipIt docker network create shipit-net # Containers join the network — communicate by name docker run -d --name redis --network shipit-net redis:7-alpine docker run -d --name shipit-api --network shipit-net \ -e REDIS_URL="redis://redis:6379" \ -p 8080:8080 shipit/api:latest # shipit-api connects to redis at hostname "redis" — Docker DNS resolves it
Chapter 6

Volumes —
persistent state
beyond the container.

Containers are ephemeral — when they're removed, their writable layer is gone. Volumes are the answer: Docker-managed storage that exists independently of any container and persists across container restarts and removals.

what happens to data when a container dies click "remove container"
# ShipIt PostgreSQL with named volume — data persists across container restarts docker volume create shipit-pgdata docker run -d \ --name postgres \ --network shipit-net \ -v shipit-pgdata:/var/lib/postgresql/data \ -e POSTGRES_DB=shipit \ -e POSTGRES_USER=shipit \ -e POSTGRES_PASSWORD_FILE=/run/secrets/pg_password \ --secret pg_password \ postgres:15-alpine # Volume lives at /var/lib/docker/volumes/shipit-pgdata/_data on host # Survives: docker stop, docker rm, container crashes # Does NOT survive: docker volume rm (explicit deletion only)
Chapter 7

Docker Compose —
multi-container
orchestration.

Docker Compose lets you define an entire multi-container application in a single YAML file and bring it up with one command. It handles network creation, volume management, dependency ordering, and environment injection.

compose stack — click any service to explore click a service
# docker-compose.yml — complete ShipIt stack services: api: build: {context: ./api, dockerfile: Dockerfile} ports: ["8080:8080"] environment: DATABASE_URL: "postgresql://shipit:${DB_PASS}@postgres:5432/shipit" REDIS_URL: "redis://redis:6379" depends_on: postgres: {condition: service_healthy} redis: {condition: service_started} healthcheck: test: ["CMD", "curl", "-f", "http://localhost:8080/health"] interval: 30s retries: 3 deploy: {resources: {limits: {cpus: "0.5", memory: 256M}}} worker: build: {context: ./worker} environment: REDIS_URL: "redis://redis:6379" depends_on: [redis] redis: image: redis:7-alpine volumes: ["redis-data:/data"] command: redis-server --appendonly yes postgres: image: postgres:15-alpine volumes: ["pg-data:/var/lib/postgresql/data"] environment: {POSTGRES_DB: shipit, POSTGRES_USER: shipit, POSTGRES_PASSWORD: "${DB_PASS}"} healthcheck: test: ["CMD", "pg_isready", "-U", "shipit"] interval: 10s retries: 5 volumes: pg-data: {} redis-data: {} networks: default: {driver: bridge}
depends_on with condition: service_healthy waits for the healthcheck to pass — not just for the container to start. The API won't start until PostgreSQL is actually ready to accept connections.
Docker Compose vs Kubernetes: Compose is for single-host multi-container orchestration — local dev, CI, simple production. Kubernetes is for multi-host orchestration, auto-scaling, and self-healing across a cluster. Use Compose for development; use Kubernetes (or Nomad) for production at scale.
Chapter 8

Container security —
the attack surface.

Containers are not a security boundary — they share the host kernel. Security requires defence in depth: non-root users, read-only filesystems, dropped capabilities, secret management, and image scanning.

security layers — click each layer to understand the threat and mitigation click a layer

Common mistakes

  • Running as root (UID 0) inside the container.
  • Storing secrets in environment variables or image layers.
  • Mounting /var/run/docker.sock into a container (full host escape).
  • Using --privileged mode — disables all security isolation.
  • Using :latest tags — non-deterministic, can't pin security patches.

Security hardening checklist

  • Non-root USER in Dockerfile — UID ≥ 1000.
  • Read-only root filesystem: --read-only.
  • Drop all capabilities: --cap-drop ALL.
  • No new privileges: --security-opt no-new-privileges.
  • Use Docker secrets / AWS Secrets Manager — not ENV vars.
  • Scan images: docker scout, Trivy, Snyk.
# Hardened docker run for ShipIt API docker run \ --read-only \ # immutable root filesystem --cap-drop ALL \ # no Linux capabilities --security-opt no-new-privileges \ --security-opt seccomp=default \ # syscall filter --user 1001:1001 \ # non-root --tmpfs /tmp \ # writable scratch space --network shipit-net \ --cpus="0.5" --memory="256m" \ shipit/api:v2.1.0@sha256:abc123 # pinned by digest, not tag

Key decisions in ShipIt

Base imagepython:3.11-slim — not alpine (glibc compatibility for native libs) not full python (250 MB savings). Always pinned to digest.
Multi-stage buildBuilder stage installs deps. Final stage copies only site-packages. Result: 800 MB → 120 MB. No pip, no gcc, no build-essential in production.
Layer cache orderrequirements.txt first, src/ last. Cache invalidated only when deps change. Build: 3 min → 8 sec on code-only changes.
SecretsDocker secrets via --secret / secrets: in Compose. Mounted as files at /run/secrets/. Never in ENV, never in image layers (they persist in history).
Health checksAll services have healthcheck. depends_on with service_healthy ensures startup ordering. Compose and Swarm use health status for routing.
Non-rootUSER appuser (UID 1001) in Dockerfile. Volume mount permissions set to 1001:1001. read-only root fs with --tmpfs /tmp for scratch space.
The one-sentence mental model: A Docker container is a process isolated by namespaces and cgroups, running on a union-filesystem image made of cached read-only layers, connected to other containers via virtual bridge networks, with persistent data stored in named volumes — all defined in a Dockerfile and orchestrated by Compose.
