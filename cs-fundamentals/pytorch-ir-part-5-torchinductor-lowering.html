TorchInductor takes a normalized ATen/FX graph and turns tensor operations into loop programs, groups compatible loops into kernels, plans temporary storage, picks tiles, then emits code for the target machine.

MAP

Where TorchInductor sits

Lowering is not graph capture, automatic differentiation, or GPU assembly. It is the middle/backend stage that makes an already-captured graph executable efficiently.

Pythoneager program, modules, control flow
TorchDynamocaptures regions and emits FX
AOTAutogradfunctionalizes; creates forward/backward graphs
Inductor lowerATen nodes → loop semantics
Schedulefuse, order, allocate, tile
CodegenTriton / C++ / optimized kernels

The key translation is from “produce this tensor” to “for these indices, load these addresses, compute this scalar/vector value, and store it there.”

SEMANTICS

Lowering

Maps each ATen operation to one or more IR nodes, preserving dtype, device, shape, stride, aliasing, and mutation semantics.

GLOBAL CHOICES

Scheduling

Builds dependencies, decides fusion groups and execution order, and reasons about when buffers become dead or reusable.

MACHINE MAPPING

Code generation

Turns a scheduled group into target code and launcher logic, choosing layouts, tiles, vector width, and kernel parameters.

Boundary to remember. FX nodes describe tensor-level operators. Inductor IR exposes index-level work. Generated code exposes threads/programs, loads, arithmetic, and stores.

Start with a tiny FX graph

One example will follow us through the entire compiler. The function is intentionally pointwise: it makes fusion and memory traffic easy to see.

example.py · source program
import torch

def score(x, bias):
    a = x + bias       # broadcast add
    b = torch.relu(a)  # pointwise activation
    c = b * 0.125       # pointwise scale
    return c

compiled = torch.compile(score, fullgraph=True)
y = compiled(torch.randn(1024, 4096, device="cuda"),
             torch.randn(4096, device="cuda"))

02

Lower tensor ops into loop semantics

Inductor’s characteristic IR is define-by-run: a Python callable describes how to compute an element for symbolic indices, while an IR node carries ranges, layout, dtype, and device.

A pointwise tensor op becomes an iteration domain plus an inner function. The inner function is replayed under different operation handlers for analysis and code generation.

  1. i0, i1 are symbolic loop indices.
  2. i0*N+i1 linearizes a row-major 2D tensor.
  3. i1 implements the broadcast bias.
  4. ops.* is abstract: analysis and codegen can reinterpret it.
conceptual Inductor-style IR · simplified
def inner_fn(index):
    i0, i1 = index
    x_val = ops.load("x", i0 * N + i1)
    b_val = ops.load("bias", i1)
    added = ops.add(x_val, b_val)
    active = ops.maximum(added, 0.0)
    return ops.mul(active, 0.125)

Pointwise(
    device="cuda", dtype=float32,
    ranges=[M, N], inner_fn=inner_fn,
    layout=FixedLayout(size=[M,N], stride=[N,1])
)

What “define-by-run” buys you

Analysis interpretation

  • ops.load records read buffers and affine/non-affine indices.
  • ops.store records writes and mutation.
  • Math ops expose dependencies and dtype conversions.
  • Symbolic expressions stay symbolic rather than forcing a concrete size.

Codegen interpretation

  • For Triton, loads become tl.load.
  • For CPU, they become pointer/vector accesses.
  • Index formulas are simplified and mapped to target loop variables.
  • Masks are generated for tiles that cross an edge.

Not everything is pointwise

REDUCTION

sum / max / softmax pieces

Has output ranges plus one or more reduction ranges. Scheduling must choose reduction strategy and partial accumulation.

TEMPLATE / EXTERN

matmul / convolution

May map to tuned templates or external libraries. Pointwise producers/consumers can sometimes become epilogues or prologues.

LAYOUT-ONLY

view / permute

May change size/stride metadata without materializing a kernel. A later consumer reads through the transformed index map.

A view is usually not a copy. permute can survive as a changed indexing formula. A materialization appears only when an eventual consumer or layout requirement demands storage.
03

Fusion is a scheduling decision

Lowering makes loops comparable. The scheduler then asks whether compatible producer/consumer work can share one kernel without violating dependencies or making the kernel worse.

K0 · add
read x,bias · write a
→
K1 · relu
read a · write b
→
K2 · mul
read b · write out

Three launches. Two full-size temporaries (a, b) are written to and read from device memory.

The fusion test, step by step

Question
Our graph
Potential blocker
Dependency-safe?
Yes: a straight producer → consumer chain.
Mutation, aliasing, ordering side effects.
Compatible iteration?
Yes: every op maps to the same [M,N] points.
Incompatible loop nests or layouts.
Legal on target?
Yes: add, max, multiply are ordinary elementwise math.
Unsupported dtype/op or external-call boundary.
Profitable?
Likely: removes launches and intermediate traffic.
Register pressure, duplicated work, poor occupancy.

Vertical fusion

Producer and consumer become one kernel: add → relu → mul. Intermediate values live in registers rather than global buffers.

Horizontal fusion

Independent loops with compatible domains share a kernel launch. This reduces launch overhead but does not remove a producer/consumer temporary.

Why “fuse everything” is wrong

  • Resource pressure: a larger fused kernel can use more registers/shared memory, reducing occupancy.
  • Recomputation: inlining a producer with multiple consumers may duplicate expensive math.
  • Layout mismatch: two loops may traverse the same values in incompatible orders.
  • Library boundaries: a tuned matrix multiplication may remain an external call, with only its epilogue fused separately.
  • Reductions: pointwise work can often fuse around a reduction, but only if the schedule preserves its accumulation semantics.

Four different memory ideas

ELIMINATION

No buffer at all

Fusion keeps an intermediate as a scalar/vector register value. Best outcome for purely internal pointwise temporaries.

REUSE

Recycle storage

After the last use, a compatible later temporary can occupy the same allocation.

IN-PLACE

Alias deliberately

An output may reuse an input only when semantic alias/mutation rules and remaining users permit it.

Peak memory is a schedule property. The same graph can have different peak memory under a different order. Earlier freeing helps memory; extra serialization may hurt parallelism. The planner works under correctness constraints first, then optimization goals.
05

Map an iteration space onto hardware

Tiling partitions a logical loop domain into blocks that fit the target’s execution and memory hierarchy. It changes how work runs, not the tensor result.

Pointwise mapping

Flatten [M,N] into xnumel=M×N. Triton program pid owns a block:

index mapping
xoffset = pid * XBLOCK
xindex  = xoffset + arange(0, XBLOCK)
mask    = xindex < xnumel
row     = xindex // N
col     = xindex % N

Three common loop shapes

Loop family
Typical axes
Core choice
Pointwise
x or x,y output axes
Block size, vectorization, contiguous traversal, edge mask.
Reduction
x outputs × r reduction
XBLOCK/RBLOCK, persistent vs split reduction, accumulation dtype.
Matrix multiply
M,N output tiles × K reduction
BLOCK_M/N/K, warps/stages, grouping for cache locality, autotuned candidates.

A matrix multiplication tile in words

  1. Pick an output tile C[m:m+BM, n:n+BN].
  2. Walk the reduction dimension K in BK-sized chunks.
  3. Load matching A and B tiles, ideally coalesced.
  4. Accumulate a BM×BN block in registers.
  5. Apply a fusable epilogue such as bias or activation.
  6. Mask and store the valid edge of C.
Tiling is a trade space, not a constant. Larger blocks improve reuse and amortize overhead, but consume more registers/shared memory. Autotuning benchmarks a bounded family of legal schedules and caches the winner for the relevant configuration.
06

Choose a code generation path

Inductor is multi-target. The target and operation family determine whether a scheduler group becomes generated loop code, a template kernel, or a call into an optimized library.

Triton

GPU generated
Best fit
Pointwise, reductions, many fused GPU kernels, template-driven matmul families.
Emits
Python-declared Triton JIT kernels using tl.load, block math, and tl.store.
Controls
Block sizes, warps, stages, masks, heuristics/autotuning metadata.

C++ / OpenMP

CPU generated
Best fit
CPU pointwise/reduction loops, vectorized loop nests, parallel outer ranges.
Emits
C++ compiled at runtime, with vector intrinsics/helpers and threaded work sharing where profitable.
Controls
Vector width, loop ordering, parallel grain size, reduction strategy.

CUDA path

GPU native ecosystem
Best fit
CUDA templates/custom kernels and external library calls when a generated Triton loop is not the selected implementation.
Emits/calls
CUDA-oriented template code or wrappers around optimized kernels such as matrix multiplication/convolution libraries.
Controls
Template choice, layout, epilogue opportunities, algorithm/autotune selection.
conceptual target form · Triton
@triton.jit
def fused_add_relu_mul(x, bias, out, n, N: tl.constexpr,
                             XBLOCK: tl.constexpr):
    idx = tl.program_id(0) * XBLOCK + tl.arange(0, XBLOCK)
    mask = idx < n
    xv = tl.load(x + idx, mask=mask)
    bv = tl.load(bias + (idx % N), mask=mask)
    y = tl.maximum(xv + bv, 0.0) * 0.125
    tl.store(out + idx, y, mask=mask)
conceptual target form · CPU loop
#pragma omp parallel for
for (int64_t i = 0; i < M*N; i += VLEN) {
    auto xv = Vectorized<float>::loadu(x + i);
    auto bv = gather_or_broadcast(bias, i, N);
    auto y  = maximum(xv + bv, 0.0f) * 0.125f;
    y.store(out + i);
}

Generated/template kernel

Inductor owns the schedule family and may fuse a surrounding epilogue into a CUDA/Triton template.

OR

External optimized call

The wrapper allocates output and invokes a tuned library kernel; nearby pointwise work may stay separate or fuse where supported.

Important nuance: “CUDA backend” is not one uniform path where every FX node turns into handwritten CUDA C++. On NVIDIA GPUs, Triton is a primary generated-kernel route; CUDA-native templates and external libraries coexist with it.

Read real generated output

This short excerpt comes from a public PyTorch issue produced with PyTorch 2.7.0+cu128 on an RTX 4090. It is intentionally brief; use the source link for the full artifact.

observed TorchInductor output · exact excerpt
@triton.jit
def triton_poi_fused_addmm_relu_threshold_backward_0(...):
    xindex = xoffset + tl.arange(0, XBLOCK)[:]
    tmp0 = tl.load(in_out_ptr0 + xindex, None)
    tmp1 = tl.load(in_ptr0 + (xindex % 128), None)
    tmp2 = tmp0 + tmp1
    tmp4 = triton_helpers.maximum(0, tmp2)
    tl.store(in_out_ptr0 + xindex, tmp4, None)
NAME

poi_fused signals a pointwise fusion group; the name includes contributing source ops.

DOMAIN

xindex is the flattened output coordinate owned by one Triton program block.

BROADCAST

% 128 maps each flattened element to the matching bias column.

IN-PLACE STORE

The kernel writes the activation result to an input/output pointer; wrapper code governs alias safety.

The wrapper is half the story

Generated files also contain a Python call(args) wrapper. Read it before judging fusion: it checks size/stride assumptions, allocates or reuses buffers, launches external kernels and generated kernels, frees references, and returns outputs. A kernel name can mention addmm even when the matrix multiplication itself is an external call and only its following bias/activation work appears in the Triton body.

Read bottom-up. Start at call(args) to see the true launch sequence. Then open each kernel body. Names summarize provenance; bodies reveal what actually fused.
08

A practical inspection workflow

Do not start by reading all compiler internals. Generate one tiny graph, keep shapes stable, and inspect one layer at a time.

run commands
# Show generated wrapper + kernels
TORCH_LOGS="output_code" python example.py

# Produce a structured compile trace directory
TORCH_TRACE=/tmp/trace python example.py

# When symbolic shapes / guards are the issue
TORCH_LOGS="dynamic" python example.py

What to look for, in order

  1. Graph count: did Dynamo create one region or graph breaks?
  2. ATen graph: which ops and decompositions reached Inductor?
  3. Scheduler groups: how many kernels, and which buffers connect them?
  4. Wrapper: external calls, allocations, reuse comments, and launch order.
  5. Kernel body: index equations, masks, loads, reduction axes, and stores.
  6. Runtime evidence: profiler kernel count, memory traffic, occupancy, and warm steady-state time.

Compile-time question

“Why did these nodes not fuse?” Inspect dependencies, iteration domains, layout, mutation, and scheduler decisions.

Runtime question

“Why is the fused kernel slower?” Inspect register pressure, memory coalescing, launch count, tile choice, and achieved occupancy.

Common reading mistakes

  • Comparing the first compiled call with eager execution; compilation cost dominates the first call.
  • Assuming fewer kernels always means faster execution.
  • Treating a generated filename or kernel name as proof of the body’s contents.
  • Ignoring stride assertions; the same shape with a different layout can select another compiled variant.
  • Ignoring dynamic-shape guards and accidentally benchmarking recompilation.
09

The complete mental model

Use these invariants to reason from source to machine code without memorizing implementation classes.

1 · GRAPH

Values and dependencies

FX/ATen says which tensor result depends on which earlier result.

2 · LOOP

Indices and addresses

Lowering says which logical output coordinates read which storage offsets.

3 · SCHEDULE

Groups and order

Scheduling chooses fusion boundaries and a legal topological execution order.

4 · MEMORY

Lifetimes and aliases

Planning decides which values need storage and when storage may be reused.

5 · TILE

Parallel decomposition

Tiling maps logical axes onto blocks, threads/vector lanes, registers, and caches.

6 · CODE

Target instructions

Codegen materializes loads, arithmetic, masks, stores, launch metadata, and wrappers.

Performance comes from moving less data, launching less often, using hardware-friendly tiles, and preserving enough parallelism. Fusion is one tool, not the goal.

Predict before you inspect

  • Pointwise chain → likely one fusion group.
  • Broadcast → modulo or multidimensional index map.
  • View/permute → changed strides, often no kernel.
  • Reduction → explicit reduction axis and accumulator.
  • Matmul → template or external kernel boundary.
  • Dead temporary → eliminated or reusable storage.
  • Edge tile → mask on loads/stores.
  • Dynamic dimension → symbol, guard, or specialization.
The nodes are dependency-compatible pointwise loops over the same iteration domain. The scheduler can inline producer expressions into the consumer, so intermediate values stay local and only the final output is stored.
The selected matrix multiplication may be an external tuned kernel without epilogue fusion for that configuration. The ReLU then becomes a separate pointwise kernel. A kernel’s provenance-rich name does not prove the matmul body is inside it.
Shape defines the logical iteration extent. Stride defines how a logical index maps to storage. Two tensors can have the same shape but require different address formulas and possibly different compiled code.
When all its uses are fused into a kernel that can carry the value in registers/local state, and no aliasing, mutation, external use, or layout constraint requires materialized storage.

Hands-on lab: prove each stage

Run these experiments in sequence on a machine with a recent PyTorch 2.x build. Keep the function tiny so every emitted line has an explanation.

Lab A · Pointwise fusion

goal: one generated pointwise kernel
def f(x, b):
    return torch.relu(x + b) * 0.125

opt = torch.compile(f, fullgraph=True)
x = torch.randn(1024, 4096, device="cuda")
b = torch.randn(4096, device="cuda")
assert torch.allclose(opt(x,b), f(x,b))

Explain: kernel count; why bias indexing differs from x; which intermediates are absent; where the edge mask comes from.

Lab B · Break compatibility

goal: create a reduction boundary
def g(x):
    centered = x - x.mean(dim=-1, keepdim=True)
    return torch.sigmoid(centered)

Explain: output axis vs reduction axis; whether mean and following pointwise work fuse; what storage is materialized; which reduction strategy appears.

Lab C · Change layout, not shape

goal: watch index formulas change
x0 = torch.randn(256, 512, device="cuda")
x1 = x0.t()  # shape [512,256], non-contiguous stride

def h(x): return torch.sin(x) + 1

Explain: whether the transpose itself launches; how strides alter the address formula; whether output layout changes.

Completion rubric

  • I can identify every kernel launch in the wrapper.
  • I can derive one load offset from shape + stride.
  • I can name the output and reduction axes.
  • I can justify one fusion and one non-fusion.
  • I can locate a buffer allocation and last use.
  • I can explain XBLOCK/RBLOCK or BM/BN/BK.
