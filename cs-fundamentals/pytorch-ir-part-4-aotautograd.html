From a dynamic tape to compiler-visible training

Autograd, ahead of time.

TorchDynamo can capture the model’s forward tensor program. Training needs the other half—the gradient computation that eager PyTorch normally creates dynamically. AOTAutograd exposes that hidden work as FX, optimizes the forward/backward boundary, then hands both graphs to a backend such as TorchInductor.

The key transformation: make parameters, tangents, gradients, saved activations, aliasing, and mutation explicit—so a compiler can reason about training as programs rather than runtime side effects.

After this guide, you can
  • read a joint graph
  • explain a partition cut
  • trace one compiled iteration
  • debug the right layer
01

The forward graph is only half the program

Inference consumes outputs. Training also asks: “How did every differentiable input contribute to the loss?”

Eager autograd: a dynamic tape

As forward operators run, the autograd engine records enough history to later execute derivative formulas. Calling backward() traverses that runtime structure.

  • Flexible and debuggable
  • Backward work is not a Python-level FX graph up front
  • Harder for a backend to fuse across gradient ops
VS

AOTAutograd: explicit programs

Run the trusted eager autograd machinery once during compilation—on tracing inputs—and record the tensor operations it performs.

  • Produces compiler-friendly forward and backward FX
  • Exposes the activation boundary
  • Enables separate backend compilation

“Ahead of time” is local, not ahead of deployment. Under torch.compile, capture usually happens lazily when a specialization is first seen. AOTAutograd means the backward graph is captured before that compiled backward executes—not that your whole model was compiled days earlier.

A tiny derivative, made explicit

s = a + b  →  u = sin(s)  →  L = Σ(u²)
dL/ds = tangent × 2u × cos(s)

The eager tape knows this relationship implicitly through autograd nodes. The AOT path materializes its operator-level computation: multiply, cosine, multiply again—normal graph nodes a compiler can schedule and fuse.

Dynamo answers

What tensor program ran?

It specializes Python execution into guarded FX graph regions and leaves unsupported Python around them.

AOTAutograd answers

What derivatives must run?

It exposes autograd’s tensor work, normalizes graph semantics, and selects what crosses the forward/backward boundary.

Inductor answers

How should it execute?

It lowers each FX graph, schedules operations, fuses compatible work, and emits target code.

03

One Dynamo graph enters; two backend graphs leave

The real path contains bookkeeping and edge cases. Keep this seven-stage invariant in your head.

1

Specialize the call

Dynamo has already captured a graph region and guards the assumptions used to build it: relevant types, tensor metadata, constants, and shape relationships.

input: FX GraphModule + example inputs
2

Flatten the world

Nested arguments and outputs are converted to a flat calling convention. Parameters and buffers become explicit graph inputs. This is easier for compilers than arbitrary Python containers and module state.

pytree → flat tuple
state → placeholders
3

Model values without real allocation

Fake tensors carry shape, dtype, device, layout, and stride metadata without requiring the real data allocation. They let tracing propagate tensor metadata cheaply; truly data-dependent behavior cannot be decided from metadata alone.

Tensor[N,D] → FakeTensor[N,D]
4

Functionalize mutation and aliases

In-place updates and views are semantically important but awkward for pure dataflow. Functionalization rewrites mutations into out-of-place equivalents and records how observable mutations or aliases must be repaired at the boundary.

add_ → add
view alias → explicit metadata
5

Run autograd while tracing

PyTorch’s own derivative formulas execute through the dispatcher on tracing tensors. Their ATen operations are recorded beside the forward work, producing a joint forward-backward graph.

primals + tangents → outputs + grads
6

Partition the joint graph

The partitioner chooses which intermediate values the forward returns for later use, and which cheap forward values the backward should recompute. The result is a forward FX graph and a backward FX graph.

joint FX → fw FX + bw FX
7

Compile and wrap

The backend compiles each graph. A generated autograd wrapper makes them look like ordinary PyTorch: forward returns user outputs while retaining saved values; backward consumes incoming tangents and returns gradients in input order.

compiled_fn(...).backward()

Why ATen-level graphs? Backends benefit from a smaller, explicit operator vocabulary. Decompositions can replace composite operators with simpler ATen operations; exact graphs vary by PyTorch version, backend, configuration, and operator.

04

Read the joint graph as a VJP program

Reverse-mode AD computes a vector–Jacobian product. The upstream gradient is a real input, conventionally called a tangent.

worked_example.py
import torch

def loss_fn(a, b):
    s = a + b
    u = torch.sin(s)
    return (u * u).sum()

a = torch.randn(1024, requires_grad=True)
b = torch.randn(1024, requires_grad=True)
compiled = torch.compile(loss_fn)
compiled(a, b).backward()
simplified — names and exact overloads may differ
def joint(primals_a, primals_b, tangents_loss):
    # forward
    s = torch.ops.aten.add.Tensor(primals_a, primals_b)
    u = torch.ops.aten.sin.default(s)
    sq = torch.ops.aten.mul.Tensor(u, u)
    loss = torch.ops.aten.sum.default(sq)

    # backward: VJP seeded by tangents_loss
    two_u = torch.ops.aten.add.Tensor(u, u)
    local = torch.ops.aten.cos.default(s)
    grad_s = tangents_loss * two_u * local
    return [loss, grad_s, grad_s]
inputs: a, b, Ḷ
forward: s=a+b; u=sin(s); L=Σu²
reverse: ū=Ḷ·2u; s̄=ū·cos(s); ā=s̄; b̄=s̄

Ḷ is the incoming cotangent for the scalar loss. With a normal loss.backward(), its effective value is 1. For non-scalar outputs, the caller supplies a matching gradient.

Joint visibility matters because the best forward boundary depends on backward needs. If the compiler sees only the forward, it cannot decide whether saving an activation is more expensive than regenerating it later.

05

Partitioning is a memory–compute contract

A partitioner is not merely drawing a line. It chooses the values that cross time from forward execution to backward execution.

Save

Forward exports an activation

The backward begins quickly because the value already exists. Cost: activation memory, lifetime extension, and often a device-memory write/read across the boundary.

Recompute

Backward recreates an activation

Forward retains less. Backward performs extra operators. This can win when those operators are cheap and fuse into nearby backward work.

Partition lab

Move the policy from “save intermediates” toward “recompute cheap pointwise work.” This is an explanatory model for the worked graph—not a measured PyTorch cost model.

What “min-cut rematerialization” is optimizing

Conceptually, the joint dataflow graph becomes a flow network. Candidate values carry costs: keeping a tensor consumes memory bandwidth/capacity; recomputing its producer consumes compute and may affect fusion. A cut separates mandatory forward work from backward-required work while choosing a legal, low-cost set of saved values. Heuristics prevent unsafe or expensive recomputation.

Good to recompute

Cheap pointwise ops

Examples: elementwise arithmetic or activations, especially when they can fuse into a backward kernel.

Often save

Expensive producers

Large matrix multiplications, convolutions, or other costly results may be poor rematerialization candidates.

Must respect

Semantics

Randomness, mutation, aliasing, views, side effects, and input requirements constrain legal cuts and rewrites.

Save-oriented forward

Return user output plus more residuals.

losss activationu activation
MORE
BYTES →

Recompute-oriented forward

Return user output plus a smaller residual set.

losss activation

This is related to activation checkpointing, but AOTAutograd can choose at an operator boundary with compiler knowledge. The win is not “recompute everything”; it is recompute the right things.

06

Two graphs, one autograd contract

The user still sees a normal tensor with a grad function. The wrapper hides a very explicit calling convention underneath.

conceptual forward FX after partition
def forward_graph(a, b):
    s = aten.add(a, b)
    u = aten.sin(s)
    sq = aten.mul(u, u)
    loss = aten.sum(sq)
    return loss, s       # loss is public; s is residual
conceptual backward FX after partition
def backward_graph(s, tangent_loss):
    u = aten.sin(s)              # rematerialized
    local = aten.mul(aten.add(u, u), aten.cos(s))
    grad_s = aten.mul(tangent_loss, local)
    return grad_s, grad_s     # gradients align with a, b
conceptual autograd.Function wrapper
class CompiledFunction(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        loss, saved_s = compiled_fw(a, b)
        ctx.save_for_backward(saved_s)
        return loss

    @staticmethod
    def backward(ctx, tangent_loss):
        (saved_s,) = ctx.saved_tensors
        grad_a, grad_b = compiled_bw(saved_s, tangent_loss)
        return grad_a, grad_b

Backward compiles lazily in a common workflow. The forward compiler is needed when the compiled function first runs; the backward compiler may not be invoked until the first backward call. This is why first-iteration timing can contain multiple compilation phases.

FIRST CALL
Dynamo specialization + AOT tracing + forward compilation

Compile work is cached for compatible future calls.

FORWARD RUN
Execute compiled forward

Return the visible loss and retain residual values selected by the partitioner.

FIRST BACKWARD
Compile if needed, then execute compiled backward

Incoming tangent + residuals become gradients for differentiable inputs.

STEADY STATE
Reuse cached specializations

Guard success avoids recapture; guard failure can trigger another specialization and compile.

07

How this enables training under torch.compile

The training speedup opportunity is larger than inference because backward often contains many small, fusible derivative operations.

Inside AOTAutograd’s useful view

  • The captured forward tensor region
  • Derivative formulas generated for that region
  • Saved activation choices
  • Forward and backward FX handed to the backend

Not automatically “the whole trainer”

  • Arbitrary Python around graph breaks
  • Data loading and host-side orchestration
  • Every optimizer implementation or hook
  • Uncaptured autograd work outside the region
a practical training loop
model = MyModel().cuda()
compiled_model = torch.compile(model)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)

for x, target in loader:
    optimizer.zero_grad(set_to_none=True)
    pred = compiled_model(x.cuda())       # captured forward region
    loss = loss_fn(pred, target.cuda())
    loss.backward()                       # compiled AOT backward for region
    optimizer.step()                      # capture depends on how loop is compiled
Fusion

Fewer launches

Derivative chains that eager mode dispatches as separate operators can become fused kernels where legality and profitability allow.

Memory

Smarter residuals

The partitioner can trade cheap recomputation for fewer saved activation bytes and better memory traffic.

Reuse

Compile once per specialization

Compatible calls reuse generated code; changing guarded assumptions may compile a new variant.

AOTAutograd ≠ Compiled Autograd

AOTAutograd traces the backward associated with a captured forward graph region and creates the forward/backward pair discussed here. Compiled Autograd is a separate feature that captures autograd-engine execution at backward runtime, potentially forming a larger backward graph across AOTAutograd boundaries and including more runtime behavior such as hooks. They can participate in the same stack, but they solve different capture-boundary problems.

Read the compiler’s evidence

Do not debug “torch.compile” as one box. Ask which representation first diverges from your expectation.

Dynamo graph

Did Python capture produce one useful region? Are graph breaks fragmenting it?

TORCH_LOGS="graph_code,graph_breaks" python train.py

Joint graph

Which primal and tangent inputs appear? Which derivative ops did autograd emit before partitioning?

TORCH_LOGS="aot_joint_graph" python train.py

Partitioned graphs

What residuals leave forward? Which forward operators reappear in backward?

TORCH_LOGS="aot_graphs" python train.py

Generated kernels

Did Inductor fuse the work? What target code and scheduling decisions resulted?

TORCH_LOGS="output_code" python train.py

09

Semantic boundaries and failure modes

AOTAutograd makes a difficult system tractable by normalizing semantics—not by pretending PyTorch is a pure functional language.

Mutation & aliasing

Functionalization is essential

An in-place update can affect every alias of the same storage. Rewriting it requires preserving observable behavior, updating inputs when necessary, and regenerating alias relationships at outputs.

Data dependence

Metadata cannot reveal values

Fake tensors know shape and stride, not data. A branch controlled by a tensor value may force a graph break or require a higher-order representation rather than ordinary tracing.

Randomness

Recompute must reproduce semantics

Blindly repeating a random operation could draw a different value. RNG handling and partition legality must preserve the program’s intended behavior.

Graph fragmentation

Small regions limit the payoff

Each Dynamo graph region gets its own AOT treatment. Frequent breaks reduce fusion scope, increase wrappers, and can raise compilation overhead.

Specialization

Guards still govern reuse

AOTAutograd does not remove Dynamo’s assumptions. New shapes, strides, dtypes, modes, or Python states can require another compiled specialization.

Private APIs

Inspect, don’t couple blindly

Low-level torch._functorch and compiler internals are useful for learning and backend development but may change. Prefer public torch.compile workflows for application code.

Performance is an empirical result, not a guarantee. Compilation adds warm-up cost; fusion and rematerialization depend on the graph, hardware, shapes, backend, and version. Measure steady-state throughput, first-step latency, peak memory, and numerical agreement.

10

Knowledge check

If you can answer these without reopening the guide, the mental model is working.

Dynamo captures Python execution into FX regions, while eager autograd’s backward work is generated and run inside the autograd engine below that Python-level capture. AOTAutograd executes the trusted derivative machinery during tracing and records those tensor operations as a graph.
Primals are the values being differentiated: inputs and lifted state. Tangents/cotangents are upstream gradients arriving at outputs; reverse-mode uses them to compute vector–Jacobian products and return gradients aligned with primal inputs.
Those extra outputs are residuals saved for backward. The wrapper hides them from the user but retains them until backward. The partitioner decides which values become residuals.
When a saved tensor would incur meaningful memory traffic and its producer is cheap enough to regenerate—especially when the repeated pointwise work fuses with surrounding backward operations. It is a graph- and backend-specific tradeoff.
Compare aot_joint_graph (what dependencies exist before the cut) with aot_graphs (what the partitioner placed in forward and backward). Then inspect backend output only if the graph-level choice looks correct.
