CHAPTER 01

Why Dynamo exists: Python is both the feature and the obstacle

PyTorch’s eager mode is loved because the program is Python. But a compiler needs a region of tensor operations it can inspect together. Dynamo builds that region without asking you to rewrite the model in a new language.

EAGER EXECUTION

One operation at a time

Python dispatches matmul, waits, dispatches relu, then dispatches add. Each op is correct and debuggable, but the next op is invisible when the current one launches.

x = a @ w          # launch 1
x = torch.relu(x) # launch 2
out = x + bias    # launch 3
GRAPH CAPTURE

A region becomes visible

The backend receives a connected graph. It can remove overhead, plan memory, and fuse compatible pointwise work. Dynamo’s job is capture; optimization belongs downstream.

a ─┐
   ├─ matmul ─ relu ─ add ─ out
w ─┘                 ↑
                    bias
Keep the layers separate in your head.Dynamo does not itself generate a fast GPU kernel. It captures an FX graph and hands that graph to a backend. With the default backend, AOTAutograd and TorchInductor do the later work.

PyTorch describes TorchDynamo as a Python-level JIT that hooks CPython’s frame evaluation API and rewrites bytecode to extract PyTorch operations into FX graphs.[1] This placement is why it can see Python control flow more faithfully than a simple “record tensor calls from one example” tracer.

CHAPTER 02

Bytecode is the seam Dynamo can intercept

CPython first compiles a function’s source into instructions for a stack machine. When Python is about to evaluate a frame, PEP 523 gives tools such as Dynamo a hook to substitute custom evaluation behavior.

Start with a tiny function

def score(x, scale):
    y = x * scale
    z = torch.relu(y)
    return z + 1

Frame means one invocation’s execution state: its code object, instruction pointer, locals, globals, and value stack. Dynamo receives this context at the moment Python would evaluate it.

Dynamo is not “turning all Python into a graph.”It extracts compilable tensor regions. Python that cannot or should not enter the graph can run in the interpreter, separated by graph breaks.

The capture loop, step by step

1 · Source tracking. Dynamo knows where a value came from—such as local x, global torch, or attribute self.training. Sources later let guards retrieve the corresponding runtime value.

2 · Variable wrapping. Concrete runtime objects become internal variable types: tensors, constants, modules, functions, lists, and other tracked forms. The wrapper controls which operations are safe to model.

3 · Bytecode interpretation. The symbolic interpreter updates its own stack and locals. A supported tensor call emits an FX node rather than eagerly performing the full data computation.

4 · Fake/meta reasoning. Tensor metadata—shape, stride, dtype, device, alias information—lets capture infer outputs without doing the expensive real tensor work. Exact internals vary by PyTorch version, but compilation reasons about metadata.

5 · Region finalization. At return or a graph break, Dynamo packages the nodes as an fx.GraphModule, sends it and example inputs to a backend, then receives a callable.

6 · Bytecode rewrite. A transformed frame calls the compiled callable. If capture had to stop, generated continuation code restores state and resumes Python at the correct instruction. The deep-dive documentation shows these compiled calls and continuation frames explicitly.[1]

CHAPTER 04

The output: a Python-level FX GraphModule

FX is both a graph data structure and executable Python module. Nodes name operations; edges are represented by nodes appearing in other nodes’ arguments.

def forward(self, L_x_, L_scale_):
    y = L_x_ * L_scale_
    z = torch.relu(y);  y = None
    out = z + 1;      z = None
    return (out,)
placeholderGraph inputs: tensor, lifted value, or state
get_attrRead a parameter, buffer, or constant from the module
call_functionCall an operator such as torch.relu
call_methodInvoke a method such as x.view(...)

Read an FX node as a tiny instruction

name    = "z"
op      = "call_function"
target  = torch.relu
args    = (y,)
kwargs  = {}
users   = {out: 1}

Names are not semantics. The node’s target, arguments, metadata, and ordering matter. The generated Python is a readable view, while the graph’s node list is the transformable IR.

Why the output is a tupleCompiler regions need an explicit interface. Values required by later Python or another graph cross the boundary as outputs, even when the original function had not returned yet.
CHAPTER 05

Guards are the contract behind specialization

A captured graph is valid only under assumptions made while capturing it. Guards are fast runtime predicates that test those assumptions before reusing a cached graph.

Incoming call
x: float32 [8, 128], cuda:0
scale: Python int 2
self.training: False
ALL
GUARDS
PASS?
YES → cache hitrun the matching compiled callable
NO → misscapture and compile a new specialization

Common guard families

Tensor match: Python class, dtype, device, grad requirement, rank, dispatch state, and—depending on dynamic-shape policy—size and stride. PyTorch’s Dynamo deep dive enumerates these tensor properties.[1]

Constant/value match: a Python scalar, string, boolean, list length, or other value that changed the traced behavior must remain compatible with the specialization.

Object identity/type: a referenced function, module, class, or global may need to be the same object or type seen during capture.

Global execution state: grad mode, autocast state, deterministic algorithms, and related thread-local state can change operator semantics, so compiled code may be guarded on them.

A guard is not an input validation feature.It protects compiler correctness. A failed guard normally means “this cached specialization does not apply,” not “the user supplied invalid data.”
CHAPTER 06

Recompilation lab: watch the cache branch

Change one runtime property, then issue a call. This simplified simulator models a static-shape policy and a specialization on training. Real guard sets are larger.

Specialization cache

Signature = dtype × shape × requires_grad × training

No calls yet. The first signature must compile.

On a miss, Dynamo does not mutate the old graph to accept the call. It captures another version and associates a new guard function with that frame. Later calls walk cached entries to find one whose guards pass.

This is powerful when variation is small and repeated—say, two sequence-length buckets. It is expensive when a Python value or shape changes nearly every iteration, producing a compile storm.

CHAPTER 07

A graph break cuts one frame into compiled islands

When Dynamo cannot represent the next behavior inside the current graph, it finalizes the graph so far, runs the unsupported portion in Python, then can resume capture after the boundary.

Graph A · compiledscore = x.sum()
pred = score > 0
→materialize values
Python · graph breakif pred:
  print("positive")
→resume frame
Graph B · compiledout = x * 2
return out

Graph breaks preserve Python semantics and avoid silent miscompilation, but they reduce optimization scope and add handoff overhead. The introductory PyTorch tutorial frames them as an intentional fallback: unsupported Python executes, then capture resumes.[2]

Python asks for a decision from tensor data

The branch cannot be chosen from metadata alone; it depends on the tensor’s runtime contents.

CHAPTER 08

Repair patterns: make the boundary intentional

“Remove every graph break” is not a sound goal. Aim for large, stable, profitable graphs and explicit boundaries around genuinely dynamic Python.

PATTERN 01

Stay in tensor land

Prefer tensor masks, where, vectorized indexing, and higher-order operators when they preserve semantics.

# tensorized branch
out = torch.where(x > 0, x.sin(), x.cos())
PATTERN 02

Use structured control flow

torch.cond represents both branches in the graph under explicit constraints, rather than asking Python to inspect tensor data.

return torch.cond(
  pred, true_fn,
  false_fn, (x,))
PATTERN 03

Isolate Python

Keep logging or opaque logic outside the compiled function, or use a deliberate disable boundary when that is the honest architecture.

@torch.compiler.disable
def log_stats(x):
  print(x.shape)

Use fullgraph=True as a diagnostic

By default, multiple graph regions are allowed. fullgraph=True requires the call to be captured as one graph and raises on the first break. That makes hidden boundaries visible early; it does not magically add support.

@torch.compile(fullgraph=True, backend="eager")
def candidate(x):
    return torch.relu(x * 2) + 1
CHAPTER 09

Dynamic shapes trade specialization for reuse

Static sizes give a backend strong facts. Symbolic sizes let one graph serve a range of inputs. The right policy minimizes total time: compile cost plus steady-state runtime.

STATIC SPECIALIZATION

One graph per guarded shape

[8,128] and [16,128] can produce separate cache entries. Backend optimization may be strong, but changing sequence lengths can trigger recompiles.

SYMBOLIC DIMENSION

One graph with a symbol

The batch dimension may become s0 plus range or relational guards. More calls reuse the graph, but the backend must generate code valid for those values.

The practical policy ladder

dynamic=None (automatic behavior): start specialized, then generalize dimensions that are observed changing when PyTorch can do so.

dynamic=True: ask Dynamo to produce more dynamic kernels up front. Some dimensions can remain specialized if they require it.

dynamic=False: keep sizes specialized; useful when shapes are fixed or already bucketed.

Dynamic shape ≠ dynamic rank.A tensor that changes from rank 2 to rank 3 is a different structural problem from a rank-2 tensor whose first size varies.

Example: stable sequence buckets

If requests arrive at lengths 117, 241, and 503, serving exact lengths may create many specializations. Padding to a few buckets (128, 256, 512) can exchange some extra arithmetic for fewer compiles and more predictable cache reuse. Whether that wins is workload-dependent—measure both compilation and execution.

CHAPTER 10

Observe before you optimize

The fastest route through a compile problem is to locate the failing layer: capture, AOTAutograd, or backend lowering. Start with a small backend and targeted logs.

torch._dynamo.explain(fn)(*args)Summarize capture

Inspect graph count, break reasons, operations, and guard information for a small reproducer.

TORCH_LOGS="graph_breaks"Find boundaries

Reports break locations and reasons in user code.

TORCH_LOGS="guards,recompiles"Find compile churn

See generated guards and which failure triggered a new specialization.

TORCH_LOGS="+dynamo,bytecode"Study internals

Verbose view of tracing and bytecode transformation; best for a tiny function.

A backend ladder that localizes failures

backend="eager"Dynamo captures FX, then eager PyTorch runs the graph. A failure here points toward capture.
backend="aot_eager"Add AOTAutograd graph tracing but no optimizing codegen. A new failure points toward AOTAutograd.
backend="inductor"Add lowering and generated kernels. A failure only here points toward the backend path.
fullgraph=TrueTurn a tolerated graph break into an immediate error for precise localization.

PyTorch’s troubleshooting guide recommends the same layer-by-layer backend strategy and documents TORCH_LOGS options for graph breaks, guards, and recompiles.[3]

Print every captured graph with a custom backend

def inspect_backend(gm, example_inputs):
    print(gm.graph)
    gm.graph.print_tabular()
    return gm.forward

compiled = torch.compile(score, backend=inspect_backend)
compiled(torch.randn(8), 2)

A backend is simply a callable that receives an FX GraphModule and example inputs, then returns a callable. Returning gm.forward makes this a transparent graph-inspection backend rather than an optimizing one.

CHAPTER 11

The cost model: cold calls pay to make warm calls cheap

Compilation is an investment. A graph that runs once may never repay capture and backend work; a stable graph in a long training or serving loop often can.

CALL 1 · COLDGuard miss → capture frame
COMPILEFX → backend pipeline → callable
CALL 2Guard hit → reuse specialization
CALL 3Guard hit → reuse specialization
NEW SHAPEGuard miss → maybe generalize or compile
total_time = capture_time
           + backend_compile_time
           + Σ guard_check_time
           + Σ compiled_execution_time
           + Σ fallback_python_time

A useful optimization reduces the whole sum—not merely kernel time.

Three pathologies to recognize

Compile storm: a changing Python value or shape creates unbounded specializations. Symptom: repeated recompilation logs and poor throughput.

Graph confetti: many tiny regions separated by breaks. Symptom: graph count is high but each graph contains few profitable operations.

Cold benchmark illusion: timing one compiled invocation includes compilation and looks slower than eager. Warm up, synchronize accelerators, and compare steady state separately from startup.

Hands-on lab: make Dynamo explain itself

Run this sequence in a clean Python environment with a recent PyTorch. Exact log formatting is version-dependent; the questions remain stable.

Exercise A · Capture one graph

import torch

def block(x, w, bias):
    h = x @ w
    return torch.relu(h + bias)

x = torch.randn(8, 64)
w = torch.randn(64, 128)
b = torch.randn(128)
report = torch._dynamo.explain(block)(x, w, b)
print(report)

Answer: How many graphs? Which ops entered the graph? Which input properties are guarded?

Exercise B · Trigger one recompile

compiled = torch.compile(block, backend="eager")
compiled(x, w, b)                    # cold
compiled(x, w, b)                    # expected cache hit
compiled(torch.randn(16, 64), w, b) # shape change

Run with TORCH_LOGS="guards,recompiles". Identify the failed predicate. Then try dynamic=True and compare.

def branchy(x):
    if x.sum() > 0:

print(torch._dynamo.explain(branchy)(torch.ones(8)))

Do not skip the before/after explanation. The point is not merely to make the error disappear; it is to see the graph topology change.

1. A guard fails. What happens next?

Correct: guards select valid specializations. A miss is a cache/capture event, not input validation.

2. Which statement best describes a graph break?

Correct: a break partitions the execution path; recompilation is about a cached specialization no longer matching.

3. Why is backend="eager" useful?

Correct: the FX graph is captured, then executed by eager PyTorch, helping isolate the compiler layer.

The durable mental modelDynamo is a guarded partial evaluator for Python frames. It specializes what it can know now, emits a graph for tensor work, preserves Python around the edges, and checks its assumptions every time it reuses the result.
