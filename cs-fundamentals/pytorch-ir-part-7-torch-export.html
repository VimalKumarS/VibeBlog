PyTorch IR · beginner → production

The contract between Python and production

torch.export freezes the tensor computation you authored in Python into a self-contained, inspectable program—with explicit inputs, state, shape rules, and failure boundaries that a downstream compiler can trust.

01 · Mental model

Export is a proof obligation, not “save model”

A Python module is open-ended: it can inspect globals, mutate objects, read files, branch on arbitrary values, or invoke unsupported libraries. A deployment runtime needs the opposite—a finite program with a stable interface. Export closes that gap.

1

Observe

Run or symbolically analyze the module with representative inputs. Record tensor operations and shape relationships.

2

Prove

Show that the captured graph represents every input allowed by the declared constraints—not just the example tensors.

3

Package

Bundle graph, parameters, buffers, constants, signature, range constraints, and verification metadata into one ExportedProgram.

KEY
Example inputs are evidence, not the entire contract.They choose dtypes, devices, ranks, container structure, and default-static sizes. dynamic_shapes widens selected dimensions; export must prove the graph remains valid throughout those ranges.

02 · Capture pipeline

What actually happens at export(...)

Think of capture as progressive removal of Python semantics. Each stage converts implicit behavior into explicit graph structure or rejects it.

Python moduleobjects · methods · control flow
Graph captureDynamo or ProxyTensor
Functionalizationmake mutation explicit
ATen IRoperator overloads
Contractsignature · constraints · state

During capture

  1. Flatten positional/keyword arguments using pytree structure.
  2. Replace real tensor reasoning with fake/symbolic tensor metadata where possible.
  3. Resolve Python decisions that can be safely specialized.
  4. Record ATen operations and higher-order operators such as cond.
  5. Collect assumptions required for the trace to stay sound.

Before return

  1. Lift parameters, buffers, constants, and mutation effects into the explicit signature.
  2. Attach shape/dtype/device metadata to graph nodes.
  3. Store symbolic-dimension ranges and relations.
  4. Run verifier checks against the export dialect.
  5. Return an object ready for transformation or serialization.
AOT
No “we’ll compile another graph later.”torch.compile can guard one specialization and recompile when it misses. Export has no Python capture process in production, so it must either cover the promised input space or fail now.
03 · ExportedProgram anatomy

More than an FX graph

The graph says what to compute. The surrounding package says how to call it, which values are model state, what shapes are legal, and whether later transformations preserved the contract.

ep = torch.export.export(model, (x,), dynamic_shapes=spec)

print(ep.graph_module.code)       # tensor program
print(ep.graph_signature)         # logical I/O roles
print(ep.state_dict.keys())       # parameters + buffers
print(ep.range_constraints)       # symbolic bounds
print(ep.module_call_graph)       # preserved hierarchy metadata

ep.validate()                     # dialect + consistency checks
runnable = ep.module()            # self-contained GraphModule
graph_module

An FX GraphModule whose calls target explicit operator overloads such as torch.ops.aten.add.Tensor.

graph_signature

Maps flat graph inputs/outputs to semantic roles: user input, parameter, buffer, constant, mutation, token, user output.

state_dict

The actual parameter and persistent-buffer tensors separated from graph code.

constraints

Legal ranges and relationships for symbolic integers that appear in shapes and indexing.

metadata

Node value metadata, stack traces, source ranges, and module-call information used by compilers and debuggers.

verifiers

Dialect-specific invariants checked when the program is created, transformed, or loaded.

Why the raw graph looks “too functional”

Downstream compilers do not want hidden object state. In the internal graph, parameters and buffers are typically explicit placeholders. The graph signature tells the runtime which placeholders should be filled from state_dict. Calling ep.module() binds those values back into a convenient module-shaped interface.

LOGICAL CALL
module(x)

Adapter work: flatten x → obtain parameters/buffers → call flat graph → apply recorded mutations → unflatten user outputs.

04 · Worked export

From a gated residual block to ATen IR

The example has model state, a dynamic batch, a static feature width, broadcasting, activation, and a residual add—enough structure to expose the full contract.

class GatedResidual(torch.nn.Module):
    def __init__(self, width=64):
        super().__init__()
        self.proj = torch.nn.Linear(width, width)
        self.register_buffer("temperature", torch.tensor(2.0))

    def forward(self, x):
        gate = torch.sigmoid(self.proj(x) / self.temperature)
        return x + gate * x
model = GatedResidual().eval()
example = (torch.randn(8, 64),)

B = torch.export.Dim("batch", min=1, max=128)
ep = torch.export.export(
    model,
    example,
    dynamic_shapes={"x": {0: B}},
    strict=True,
)

assert torch.allclose(
    model(example[0]), ep.module()(example[0])
)
# Simplified for readability; exact names vary by PyTorch version.
def forward(p_proj_weight, p_proj_bias, b_temperature, x):
    linear = torch.ops.aten.linear.default(x, p_proj_weight, p_proj_bias)
    div    = torch.ops.aten.div.Tensor(linear, b_temperature)
    gate   = torch.ops.aten.sigmoid.default(div)
    mul    = torch.ops.aten.mul.Tensor(gate, x)
    add    = torch.ops.aten.add.Tensor(x, mul)
    return (add,)

# graph signature classifies p_*, b_*, x, and add
# range constraints include: 1 ≤ batch ≤ 128
  1. Object access disappears. self.proj is no longer a Python object lookup.
  2. Module calls decompose. nn.Linear becomes an ATen linear operator with weight and bias inputs.
  3. State is classified. The weight/bias are parameters; temperature is a buffer; x is the user input.
  4. The batch is symbolic. Node metadata can carry a shape like [s0, 64], while s0 is bounded.
  5. The width stays static. Inputs with width other than 64 violate the contract.
TRY
Inspect three views, not one.print(ep) gives a readable package summary; ep.graph.print_tabular() shows node flow; node.meta["val"] exposes inferred shapes/dtypes.
05 · Strict vs non-strict

Two capture mechanisms, one contract target

The choice changes how Python is analyzed during capture. It does not turn export into a best-effort tracer, and it does not permit graph breaks.

DEFAULT

Strict strict=True

TorchDynamo symbolically interprets Python bytecode and records conditions needed for correctness.

  • Stronger analysis of Python behavior
  • Catches unsupported constructs early
  • Best first choice for production
  • Smaller supported Python surface
  • Errors on many custom context managers or opaque calls
ESCAPE HATCH

Non-strict strict=False

The ordinary Python interpreter runs with ProxyTensors; tensor operations are recorded as they execute.

  • Supports more benign Python scaffolding
  • Often unblocks third-party modules
  • Python values/control may specialize silently
  • Capture executes side effects in Python
  • Requires stronger differential testing

A diagnostic example

class Wrapper(torch.nn.Module):
    def forward(self, x):
        with harmless_logging_context():  # no tensor semantic effect
            return x.sin() + x.cos()

# strict=True may reject the unsupported context manager.
# strict=False executes it and records only tensor operations.
ep = torch.export.export(Wrapper(), (torch.ones(3, 3),), strict=False)
RISK
“It exported” is not proof that Python behavior was preserved.If the context manager changes tensor behavior indirectly, reads data, or mutates state, non-strict capture can record only the path observed during export. Compare outputs across boundary cases and audit the graph.

Practical escalation ladder

1 · Keep strict

Rewrite obvious graph breaks, use supported control-flow operators, and move preprocessing out of forward.

2 · Isolate

Export the tensor-only core while keeping tokenization, logging, I/O, and business logic in the host application.

3 · Use non-strict

Only when unsupported Python is operational scaffolding—not part of numerical semantics—and add parity tests.

06 · Dynamic shapes

Static by default, dynamic by declaration

A dynamic dimension is a symbolic integer with bounds and relationships. It is not “accept anything.” Precise constraints create a larger legal input set without throwing away compiler knowledge.

B = torch.export.Dim("batch", min=1, max=32)
S = torch.export.Dim("seq",   min=8, max=2048)

example_ids  = torch.randint(0, 32000, (2, 128))
example_mask = torch.ones(2, 128, dtype=torch.bool)

spec = {
    "input_ids":     {0: B, 1: S},
    "attention_mask":{0: B, 1: S},
}
ep = torch.export.export(model, (example_ids, example_mask),
                         dynamic_shapes=spec)

What the shared symbols say

Both tensors share the same B and S, so their batch and sequence lengths must match. Reusing the same Dim expresses equality.

What remains specialized

Dtype, rank, container structure, and every dimension you did not mark dynamic remain tied to the export contract.

Derived dimensions

Relations can be affine. If an internal or second input dimension is structurally twice another, represent it as 2 * S rather than declaring an unrelated symbol. This lets export and later compilers preserve the relationship.

S = torch.export.Dim("tokens", min=4, max=512)
dynamic_shapes = {
    "x":      {1: S},
    "packed": {1: 2 * S},
}
DEBUG
ConstraintViolationError is often a suggested-spec generator.The error explains which symbolic assumption your code introduced and may suggest a corrected Dim relation or tighter bound. Read it as a proof failure, not a random tracing failure.
07 · Guards become runtime boundaries

From “this was true while tracing” to “this must be true when running”

Capture encounters assumptions. Export must classify each one: prove it from declared constraints, specialize it into the contract, encode it as a runtime check, or reject the program.

Capture-time fact

x.shape[1] % 8 == 0
x.shape[0] ≤ 32
mask.shape == x.shape[:2]

→

Export decision

Proved: omit redundant check
Input contract: store shape constraints
Deferred: emit graph assertion
Unprovable: fail export

Runtime contract simulator

Contract: 1 ≤ batch ≤ 32, 8 ≤ seq ≤ 2048, and seq % 8 == 0.

ACCEPT · all assertions hold

Explicit semantic checks with torch._check

class BlockedAttention(torch.nn.Module):
    def forward(self, x):
        torch._check(x.shape[1] % 8 == 0,
                     "sequence length must be block-aligned")
        return attention_kernel(x)

# The condition is symbolic. If export cannot prove it for the
# entire declared range, the assertion can remain in the graph.

Input guards

Rank, dtype, device, static sizes, dynamic bounds, and cross-input equalities are enforced at the exported module boundary. A bad input should fail before unsafe computation.

Inline runtime asserts

Checks involving symbolic or data-dependent values may appear as assertion operators/tokens in the graph when export supports deferring them. They remain part of execution.

NUANCE
Not every Dynamo guard is copied verbatim into the graph.Export re-expresses required facts through signature checks, symbolic range constraints, specialization, and graph assertions. The result is a deployment contract, not a raw guard dump.
08 · State & mutation

Side effects become explicit dataflow

A compiler cannot safely optimize a hidden write to module state. Export functionalizes many tensor mutations and records mutated buffers or user inputs in the output signature.

class Counter(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.register_buffer("seen", torch.zeros(()))

    def forward(self, x):
        self.seen.add_(x.shape[0])
        return x / self.seen.clamp_min(1)

# Conceptual flat return:
# (updated_seen, user_output)
# graph_signature says updated_seen mutates buffer "seen".

Parameters

Read-only learned state for inference. Lifted into graph inputs and mapped back to named entries.

Buffers

Non-parameter state. Persistent buffers live in state_dict; mutations are represented explicitly.

Constants

Tensor constants or lifted custom objects needed by the graph but not user inputs.

DESIGN
Prefer an inference-pure boundary.Move metrics, caches, tokenization, random policy, and request bookkeeping outside the exported module. If state must evolve, make the update visible and test repeated calls—not just call one.
09 · Transform safely

Rewrite the IR without dropping its contract

An ExportedProgram is designed as a compiler handoff. Transformations must preserve graph-signature roles, symbolic constraints, and verifier invariants—not merely produce numerically plausible FX code.

Decomposeremove composite ops

# Lower composite ops toward a smaller Core ATen set.
core_ep = ep.run_decompositions()
core_ep.validate()

# Inspect every target your backend must support.
ops = sorted({str(n.target) for n in core_ep.graph.nodes
              if n.op == "call_function"})
print(*ops, sep="\n")

# Serialize the program contract—not arbitrary Python objects.
torch.export.save(core_ep, "model.pt2")
reloaded = torch.export.load("model.pt2")
reloaded.validate()

Safe pattern

Use export-aware decomposition/transform APIs, validate, re-run parity tests, and preserve source/shape metadata where possible.

Risky pattern

Pull out graph_module, mutate nodes freely, then assume the old signature and constraints still describe the new graph.

11 · Failure lab

Read errors by category

Export failures are usually telling you which hidden Python or shape assumption could not be made portable. Classify first; patch second.

Data-dependent Python control flow

Symptom: branching on if x.sum() > 0 requires reading tensor data into Python.

Fix: express tensor control flow with structured operators such as torch.cond, or move the branch outside the exported region. Both branches must satisfy output/metadata rules.

Unexpected static specialization

Symptom: a second batch size fails although the math should support it.

Fix: mark the dimension with Dim, reuse symbols for equality, then inspect range_constraints. Do not mark every dimension dynamic reflexively; dynamic freedom costs optimization information.

ConstraintViolationError

Symptom: declared range says a symbol varies freely, but Python indexing or a branch requires a narrower range or relation.

Fix: enable dynamic-shape logs, read generated suggestions, and decide whether to rewrite the model or tighten the public contract. Never copy a suggestion without checking it matches serving requirements.

Unsupported Python in strict mode

Symptom: Dynamo reports an unsupported builtin, custom context manager, descriptor, or extension call.

Fix: remove/isolate it first. Consider strict=False only when that code does not influence tensor semantics, then differential-test multiple inputs.

Missing fake/meta implementation for a custom op

Symptom: capture cannot infer the custom operator’s output shape/dtype without executing a real kernel.

Fix: define the custom op schema and register a fake implementation that computes output metadata from input metadata. Register backend kernels separately.

Mutation, aliasing, or object side effects

Symptom: writes to global objects, Python lists, arbitrary attributes, or aliased tensors cannot be safely represented.

Fix: return updated tensor state explicitly, use registered buffers, or keep the stateful shell outside the tensor core.

Serialization/version mismatch

Symptom: a saved .pt2 artifact fails to load under another PyTorch build or operator set.

Fix: treat runtime, exporter, opset, custom-op libraries, device stack, and model artifact as one tested release unit. Keep the original checkpoint so you can re-export.

12 · Production recipe

An end-to-end export checklist

Treat export as an API release. The artifact is ready when its accepted input space, semantics, operator set, and runtime compatibility are all tested.

1

Define the boundary

  • Set eval() and inference mode deliberately.
  • Move tokenization/I/O/request policy outside.
  • Document tensor names, dtypes, ranks, layouts, devices.
  • Decide whether state mutation is allowed.
2

Design constraints

  • Pick realistic min/typical/max dimensions.
  • Reuse Dim objects for equality.
  • Encode derived affine dimensions.
  • Add semantic torch._check assertions.
3

Capture strict first

  • Export representative inputs.
  • Classify every failure.
  • Audit graph, signature, state, constraints.
  • Use non-strict only with a written reason.
4

Prove parity

  • Random inputs across the entire legal range.
  • Boundary cases at every min and max.
  • Expected failures just outside bounds.
  • Repeated calls for mutable state.
5

Lower & package

  • Decompose to backend-supported ops.
  • Compile for exact target hardware.
  • Save manifests: versions, hashes, constraints.
  • Load in a clean runtime environment.
6

Operate

  • Validate inputs before expensive execution.
  • Monitor contract violations separately.
  • Canary numerical drift and performance.
  • Keep rollback artifact and source checkpoint.

Minimal reproducible harness

def export_and_check(model, example, dynamic_shapes, samples):
    model = model.eval()
    with torch.inference_mode():
        ep = torch.export.export(model, example,
                                 dynamic_shapes=dynamic_shapes,
                                 strict=True)
        ep.validate()
        deployed = ep.module()
        for args in samples:
            eager = model(*args)
            actual = deployed(*args)
            torch.testing.assert_close(actual, eager)
        torch.export.save(ep, "model.pt2")
        loaded = torch.export.load("model.pt2")
        loaded.validate()
        return loaded
DONE
The artifact is not “the model.”It is one tested compilation of a model version, export code, input contract, operator set, weights, and target assumptions. Production reliability comes from versioning that whole tuple.
13 · Knowledge check

Can you reason from the contract?

Answer before revealing feedback. These are the distinctions that matter in design reviews and compiler interviews.

1. A torch.compile graph guard fails in production. What can happen that export cannot rely on?

Correct: JIT compilation can re-enter Python and compile another graph. An exported deployment artifact must reject or already cover the input.

2. Two inputs must always share batch size. What is the clearest shape specification?

Correct: one shared symbol expresses equality directly; same numeric bounds alone do not.

3. Strict export fails on a logging context manager. Your first move?

Correct: simplify the tensor boundary first. Non-strict is a deliberate fallback only after you establish the Python scaffolding has no tensor-semantic effect.

4. Why inspect graph_signature as well as graph_module?

Correct: the signature says which placeholders are parameters, buffers, constants, or user inputs—and which outputs represent mutation.

5. Which statement about dynamic shapes is accurate?

Correct: dynamic means symbolic under a declared contract, not unconstrained.
