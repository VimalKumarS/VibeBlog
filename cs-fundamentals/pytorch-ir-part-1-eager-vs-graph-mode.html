00 · ORIENTATION

Start with the right mental model

There are two actors. Python on the CPU decides what to do. The GPU executes highly parallel kernels over tensors. PyTorch’s job is to translate your convenient Python operations into work those devices can perform.

ACTOR A
Python runtime

Runs control flow, objects, loops and your model code. It is flexible and sequential.

BRIDGE
PyTorch dispatcher

Selects an implementation based on device, dtype, autograd state and other dispatch keys.

ACTOR B
Device kernels

Perform tensor math on CPU, GPU or another accelerator. A GPU kernel is the device-side program; a kernel launch is one invocation of it.

Two “graphs” that beginners often mix upAutograd graph records how outputs depend on inputs so gradients can be computed. A compiler graph is an intermediate program representation used to analyze and transform execution. They can describe related math, but they exist for different jobs.
Operation / op
A tensor-level action such as add, relu, or matmul.
Kernel
Executable device code. One PyTorch op may map to one kernel, several kernels, or a vendor-library call.
IR
Intermediate representation: a compiler-readable form between source Python and final machine/device code.
Graph
A useful IR where nodes are values/operations and edges encode data dependencies.
01 · DEFINE-BY-RUN

Eager mode: execute now, discover later

In eager execution, Python reaches an operation and PyTorch runs it immediately. The result is a real tensor you can inspect, branch on, print, or feed into arbitrary Python. There is no requirement to describe the entire computation in advance.

A tiny eager program
import torch

def block(x):
    y = x + 1             # run add now
    z = torch.relu(y)      # run relu now
    out = z * 2           # run multiply now
    return out

x = torch.tensor([-2., 0., 3.])
print(block(x))          # tensor([0., 2., 8.])

What happens for each line?

CPU / Python
dispatch addwait / enqueuedispatch reluwait / enqueuedispatch mul
GPU stream
launch gapadd kernelgaprelu kernelgapmul kernel

Conceptual timeline—not to scale. CUDA launches are normally asynchronous, so “wait” here means coordination/dispatch opportunity, not necessarily a blocking CPU wait.

Why eager feels great

  • Ordinary Python control flow
  • Immediate values and familiar debugging
  • Incremental execution
  • Dynamic shapes and structures feel natural

What eager hides

  • The next operation is unknown to the current one
  • Temporary tensors become materialized boundaries
  • Each dispatch and launch has fixed overhead
  • Global scheduling choices are unavailable

Important: eager is not automatically slow. Large matrix multiplications can spend most of their time inside a highly optimized library kernel, making Python overhead small. Compilation helps most when overhead, memory traffic, or missed fusion is material.

02 · TRACE ONE TENSOR

Worked example: three ops, two hidden temporaries

Follow one vector through relu(x + 1) * 2. The arithmetic is simple; the execution cost comes from moving every element and crossing operation boundaries.

x = [-2, 0, 3] → x+1 = [-1, 1, 4] → ReLU = [0, 1, 4] → ×2 = [0, 2, 8]

Eager: materialize each stage

write temp z3 values
read temp z3 values

VS

Possible fused kernel

+1, ReLU, ×2in registers

The important saving is not “three Python lines become one.”The useful transformation is that intermediate values can stay on-chip instead of making round trips through device global memory—and three launches can become one. A compiler can consider this only after it sees the connected operations together.

Generalized to N elements

Ignoring caches and assuming one read or write per displayed transfer, the eager sketch moves roughly 6N elements; the fused sketch moves roughly 2N elements. This is a teaching model, not a promise: actual generated code, caching, dtype, layout and hardware determine real traffic.

03 · PERFORMANCE MODEL

Where does eager time go?

Tstep ≈ TPython + Tdispatch + Σ Tlaunch + Σ Tkernel + Tmemory + Tsync

This is a conceptual decomposition. Terms can overlap because accelerators execute asynchronously, but it gives you a diagnostic vocabulary.

A

Python + framework overhead

Bytecode interpretation, module hooks, dispatcher selection and operator setup happen around the math. Tiny ops make this overhead visible.

B

Kernel launch overhead

Submitting work has a fixed cost. Hundreds of tiny kernels can keep the GPU underfed even when each kernel is individually fast.

C

Global-memory traffic

Elementwise math does little arithmetic per byte. Writing and rereading intermediate tensors can dominate the cost.

D

Synchronization

Calling .item(), printing a CUDA tensor, or data-dependent CPU control flow may force the host to wait for device data.

04 · THE COMPILER’S VIEW

Graph mode: represent first, execute later

Graph mode captures a region of tensor computation as data. Instead of immediately running every operation, the system builds a representation that another program—the compiler—can inspect, transform and lower.

Why call it an intermediate representation?

It is intermediate because it is not your original Python and not yet executable GPU machine code. It deliberately keeps the facts a compiler needs: operation kind, inputs, outputs, dependencies and often metadata such as shape, dtype, layout, aliasing and mutation.

SOURCE
Python

Readable, dynamic, rich semantics.

IR
Graph

Explicit values and dependencies; easy to analyze.

TARGET
Kernel code

Specialized for device and workload.

A simplified FX-style rendering

class GraphModule(torch.nn.Module):
    def forward(self, x):
        add  = x + 1
        relu = torch.relu(add); add = None
        mul  = relu * 2;       relu = None
        return (mul,)

The assignments to None communicate that references are dead in generated Python; they are not mathematical operations. The graph’s core semantics are the dependency chain x → add → relu → mul.

Graph mode does not necessarily mean “static forever.”Modern PyTorch captures and specializes regions at runtime. It can cache compiled variants, guard assumptions, and return to Python around unsupported behavior. “Graph” describes the representation; “JIT” describes when compilation happens.
05 · WHY COMPILE?

Whole-graph visibility creates options

The compiler is not valuable because a graph looks tidy. It is valuable because the graph proves which transformations preserve the program’s meaning.

01

Fuse operations

Combine compatible producer/consumer ops so intermediates can remain in registers or shared memory, reducing launches and global-memory traffic.

02

Remove redundant work

Eliminate dead values, fold constants, simplify algebra and reuse common subexpressions when semantics allow.

03

Plan memory

See tensor lifetimes, reuse buffers, reduce peak allocations and choose when a value must be materialized.

04

Schedule and tile

Choose iteration order, thread/block mappings, tiling and vectorization for the target hardware.

05

Specialize

Generate code for known dtypes, devices, ranks or shape relations. Less general code can be faster—if guarded correctly.

06

Generate for many targets

The same high-level region can lower toward Triton/CUDA-style GPU code or C++ CPU code through different backends.

Three framework dispatches, three launches, and visible intermediate boundaries.

What compilers cannot simply do

They cannot reorder through a true data dependency, discard a visible side effect, break aliasing semantics, change numerics beyond allowed tolerances, or guess which branch runtime data will choose. Correctness constrains every optimization.

06 · PYTORCH 2 PREVIEW

Where this fits in torch.compile

At a high level, PyTorch 2 separates graph capture, training-graph preparation and backend code generation. Later guides will open every box; for now, focus on the contract between them.

Your Pythoneager-style model code
→
TorchDynamocaptures Python regions into FX graphs; creates guards
→
AOTAutogradexposes forward/backward graphs for training
→
TorchInductorlowers, schedules, fuses and generates code
→
Device codeTriton-style GPU kernels or C++ CPU code
The crucial separationTorchDynamo’s main job is capture, not GPU optimization. TorchInductor is the default compiler backend that converts captured graphs into optimized implementation code. AOTAutograd makes training’s backward work visible ahead of execution.

First call vs repeated calls

Cold path

guard check → capture → compile → run

Can be much slower than eager because compilation itself costs time.

Warm path

guard check → cached compiled code → run

This is where runtime savings can repay the one-time compilation investment.

07 · COST / BENEFIT

Compilation is an investment, not free speed

Potential payoff

  • Fewer kernel launches
  • Less temporary memory traffic
  • Lower Python overhead
  • Hardware-aware generated code
  • Reuse over many iterations

Compiler tax

  • Capture and code-generation latency
  • More complex debugging
  • Recompiles when assumptions change
  • Graph breaks reduce optimization scope
  • Not every workload gets faster
Break-even iterations ≈ compile time ÷ (eager time − compiled time)

Example: if compilation costs 2 seconds, eager takes 20 ms/iteration, and the warm compiled path takes 15 ms/iteration, the saving is 5 ms per iteration. The break-even point is about 400 iterations. These numbers are illustrative; benchmark your model.

When each mode is a sensible default

Eager-first

  • Developing and debugging
  • One-off or short-lived runs
  • Highly irregular Python behavior
  • Operations already dominated by large vendor kernels

Compile-candidate

  • Repeated training or inference steps
  • Stable tensor programs
  • Many elementwise/reduction operations
  • Profiles show launch gaps or memory-bound chains
MYTH

“Graph mode means rewriting your model in a separate graph language.” Modern torch.compile is designed to capture ordinary PyTorch programs with minimal source changes.

MYTH

“One graph becomes one kernel.” A graph may produce multiple kernels, library calls and runtime logic. Fusion is selective and legality/profitability dependent.

MYTH

“Compiled is always faster.” Cold-start cost, graph breaks, recompilation, small workloads and already-efficient kernels can erase the win.

08 · HANDS-ON LAB

Run your first fair eager-vs-compiled experiment

The goal is not to chase a particular speedup. It is to learn how to separate compilation time from steady-state execution and verify identical results.

Install a recent PyTorch 2.x build

Use the official selector for your OS and accelerator. This exercise also runs on CPU, but kernel fusion behavior differs by backend.

Choose a repeatable tensor function

Our chain mixes elementwise operations that a compiler may fuse.

Compile once, warm up both paths

The first compiled call includes capture/code generation. Warm-up also stabilizes caches and device initialization.

Synchronize accelerator timing

CUDA launches are asynchronous. Synchronize immediately before and after a measured region or use CUDA events.

Compare medians and validate output

Use many iterations, report the environment, and check numerical equivalence.

Complete teaching script
import time
import statistics
import torch

device = "cuda" if torch.cuda.is_available() else "cpu"

def f(x):
    return torch.relu(x + 1) * 2

compiled_f = torch.compile(f)
x = torch.randn(4096, 4096, device=device)

def sync():
    if device == "cuda":
        torch.cuda.synchronize()

def measure(fn, repeats=30):
    times = []
    for _ in range(repeats):
        sync()
        t0 = time.perf_counter()
        y = fn(x)
        sync()
        times.append((time.perf_counter() - t0) * 1e3)
    return y, statistics.median(times)

# Warm-up: compilation happens on early compiled calls.
for _ in range(5): f(x)
for _ in range(5): compiled_f(x)

y_eager, eager_ms = measure(f)
y_comp, comp_ms = measure(compiled_f)

assert torch.allclose(y_eager, y_comp)
print(f"device={device}")
print(f"eager median:   {eager_ms:.3f} ms")
print(f"compiled median:{comp_ms:.3f} ms")

Inspect instead of guessing

# Run from a shell to see captured graphs and graph breaks.
TORCH_LOGS="graph_code,graph_breaks,recompiles" python lab.py

# Or inspect a function programmatically.
print(torch._dynamo.explain(f)(x))
Read output as evidence, not as a grade.Look for how many graphs were captured, where breaks occurred, and whether guards cause recompilation. Internal debug formats can change between PyTorch releases.

Common benchmarking mistakes

Timing the first compiled call

You measure compile + execute, then compare it to eager execute only.

No GPU synchronization

You time queue submission while kernels finish after the timer stops.

No correctness check

A fast answer is meaningless if outputs differ beyond expected tolerance.

Only one iteration

Noise, cache state and startup effects dominate. Use warm-up and a distribution.

09 · DYNAMIC PYTHON

Graph breaks and guards: the price of flexibility

PyTorch does not pretend arbitrary Python is one static tensor graph. It preserves semantics with two mechanisms that you will study deeply in Part 2.

MECHANISM A

Graph break

Capture ends before code that cannot safely remain in the current graph. Python runs that section, and capture may resume afterward. Correctness survives; optimization scope shrinks.

MECHANISM B

Guard

A runtime condition records an assumption used by compiled code—for example dtype, device, rank, shape relation, object identity or global state. If it fails, PyTorch may recompile another variant.

Data-dependent Python branch
def route(x):
    y = torch.sin(x)
    if y.sum() > 0:     # GPU value decides Python control flow
        y = y * 2
    return torch.cos(y)

→

→

A graph break is not necessarily a bug. It is an honest boundary. The performance question is whether the break is rare and coarse, or whether it fragments a hot loop into many tiny regions.

Guard intuitionCompiled code can be fast because it is specialized. A guard is the receipt for that specialization: “this code is valid only while these assumptions hold.”

11 · KEEP THIS

Glossary, summary and sources

Eager
Execute operations as Python encounters them.
Graph mode
Capture a computation region as a program representation before executing optimized code.
FX graph
PyTorch’s graph representation built from nodes in a GraphModule.
Fusion
Combine operations into fewer kernels or implementation boundaries.
Specialization
Generate code using assumptions about inputs or state.
Guard
A runtime check that validates specialization assumptions.
Graph break
A boundary where capture stops and Python execution resumes.
Lowering
Translate a higher-level representation into a more implementation-specific one.
If you remember only one sentenceEager mode optimizes for immediate, flexible execution; graph mode pays to represent a region so a compiler can optimize relationships between operations.
