The core idea

An IR is a useful abstraction. Each level forgets some source detail and exposes a new optimization. Lowering trades semantic richness for execution detail without changing the result.

02

Graphs are programs made inspectable

Once code is data, a compiler can query users, replace nodes, prove liveness, estimate cost, and emit another program.

Read an FX-style graph

representative outputSSA-like names
graph():
  %x     = placeholder[target=x]
  %w     = placeholder[target=w]
  %bias  = placeholder[target=bias]
  %scale = placeholder[target=scale]
  %matmul = call_function[target=operator.matmul](%x, %w)
  %add    = call_function[target=operator.add](%matmul, %bias)
  %relu   = call_function[target=torch.relu](%add)
  %mul    = call_function[target=operator.mul](%relu, %scale)
  return %mul
OpcodeRoleExample
placeholderFunction/module inputx, w
get_attrRead stored parameter/bufferself.weight
call_functionInvoke function/operatortorch.relu
call_methodInvoke method on a valuex.view(...)
call_moduleInvoke a child moduleself.linear
outputDeclare return valuesreturn mul

IR metadata can carry shape, dtype, stride, device, aliasing, mutation, source location, symbolic dimensions, and side-effect information. The op says what; metadata helps decide how.

SEMANTIC IR

“Matrix multiply these tensors”

Compact and meaningful; good for algebraic rewrites. Too vague to launch hardware.

SCHEDULED IR

“Each program handles 256 outputs”

Explicit tiles, indexing, memory spaces, and synchronization; good for code generation.

SSA intuition: each produced value has one name, making use-def chains explicit. FX is not identical to LLVM SSA, but “one node produces a value used by later nodes” is the right reading model.
03

Capture: FX versus TorchDynamo

FX is the graph toolkit. Symbolic tracing is one frontend. TorchDynamo is the richer Python frontend behind torch.compile.

FX SYMBOLIC TRACE

Run with Proxy values

Operations on proxies are recorded. Clean and teachable, but Python control flow depending on a proxy cannot be decided without specialization.

TORCHDYNAMO

Analyze Python bytecode

Intercepts frame execution, captures tensor operations into FX graphs, emits continuation bytecode, and guards assumptions.

Lab 1 — inspect FX

import torch
from torch.fx import symbolic_trace

class Block(torch.nn.Module):

gm = symbolic_trace(Block())
print(gm.graph)
gm.graph.print_tabular()

Lab 2 — write an FX rewrite

identity_mul_pass.py
import operator, torch
from torch.fx import symbolic_trace

def f(x):
    return torch.sin(x) * 1

gm = symbolic_trace(f)
for node in list(gm.graph.nodes):
    if node.op == "call_function" and node.target is operator.mul:
        left, right = node.args
        if right == 1:
            node.replace_all_uses_with(left)
            gm.graph.erase_node(node)

gm.graph.lint()   # check graph invariants
gm.recompile()    # regenerate forward()
sample = torch.randn(8)
torch.testing.assert_close(gm(sample), f(sample))

Guards make dynamic Python safe

Compilation specializes. A guard states the specialization’s contract. If a new call satisfies every guard, reuse the artifact; otherwise compile another version or fall back.

Graph breaks

A graph break ends one captured region, returns to Python, then may begin another graph. Correctness survives; fusion across the boundary does not.

data-dependent Python branch
def unstable(x):
    y = torch.sin(x)
    if y.sum().item() > 0:  # tensor value escapes into Python
        y = y * 2
    return torch.cos(y)
Graph A: sin + sum→Python: item + if→Graph B/C

Compiler-friendly rewrite

branchless tensor dataflow
def stable(x):
    y = torch.sin(x)
    factor = torch.where(y.sum() > 0, 2.0, 1.0)
    return torch.cos(y * factor)

05

AOTAutograd makes training compilable

Dynamo captures the forward’s Python-visible tensor operations. Training also needs backward operations normally created by eager autograd. AOTAutograd exposes those computations ahead of steady-state execution.

Dynamo FX forward→functionalize→joint fwd+bwd→partition→compile each

Why functionalization matters

Mutation and aliasing make reordering unsafe. If a view shares storage and an in-place update modifies it, moving nodes can change visible behavior. Functionalization rewrites many mutations/views into functional values plus explicit bookkeeping.

SOURCE
v = x.view(-1)
v.add_(1)
return x

v aliases x; changing one changes the other.

FUNCTIONAL IDEA
v = view(x)
v2 = add(v, 1)
x2 = view_inverse(v2)
return x2

Mutation becomes a value; alias effects become explicit.

Worked joint graph

For y = relu(x @ w + b) * s and upstream gradient g:

mathematical structure · op spellings varyforward + backward
# forward
mm     = aten.mm(x, w)
pre    = aten.add(mm, b)
mask   = aten.gt(pre, 0)
relu   = aten.relu(pre)
y      = aten.mul(relu, s)

# backward, now compiler-visible
g_relu = aten.mul(g, s)
g_pre  = aten.where(mask, g_relu, 0)
g_x    = aten.mm(g_pre, aten.t(w))
g_w    = aten.mm(aten.t(x), g_pre)
g_b    = aten.sum(g_pre, dim=0)
g_s    = aten.sum(aten.mul(g, relu))
return y, g_x, g_w, g_b, g_s

Save activations

memory ↑

Keep forward intermediates. Less recomputation, more device memory.

Recompute activations

compute ↑

Save fewer values and recreate them in backward.

Key distinction: eager autograd records a dynamic tape each run. AOTAutograd uses PyTorch’s dispatcher/autograd machinery to produce compiler-visible forward/backward graphs and a partition between them.

06

Passes: ordinary work behind “compiler magic”

Most optimizations are local, testable rewrites performed at the IR level where their preconditions are visible.

Decomposition

Rewrite a complex op into a smaller core set.

layer_norm → primitives
Constant folding

Evaluate work with compile-time inputs.

x × 1 → x
DCE

Erase nodes that cannot affect outputs.

unused → gone
CSE

Reuse identical pure expressions where effects allow.

sin(x) twice → once
Fusion

Combine compatible producer/consumer loops.

add + relu + mul
Layout

Choose strides/tiling to reduce future cost.

coalesced access
Scheduling

Choose blocks, warps, reduction strategy, launch shape.

loops → GPU
UNFUSED EPILOGUE
3 launches

Add, ReLU, and multiply each touch global memory; full-size intermediates live between them.

FUSED EPILOGUE
1 launch

Load matmul output, bias, and scale; compute in registers; write final output.

Why not fuse everything?

  • Register pressure can reduce occupancy.
  • Neighbors may want incompatible schedules/layouts.
  • GEMM/reductions often belong in tuned templates or libraries.
  • Fusion may duplicate an expensive producer with multiple consumers.
  • Compile time and generated code size matter.
Optimization is constrained search. Fewer kernels is a heuristic. The goal is lower end-to-end cost with equivalent semantics and acceptable numerics.

    op="mm", inputs=[x,w], layout=FixedLayout([32,256]))

    Representative generated Triton epilogue
    fused_epilogue.py
    @triton.jit
def fused_bias_relu_scale(mm_ptr, bias_ptr, scale_ptr, out_ptr,
                          n: tl.constexpr, COLS: tl.constexpr,
                          BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n
    cols = offsets % COLS
    mm = tl.load(mm_ptr + offsets, mask=mask)
    bias = tl.load(bias_ptr + cols, mask=mask)
    scale = tl.load(scale_ptr)
    out = tl.maximum(mm + bias, 0.0) * scale
    tl.store(out_ptr + offsets, out, mask=mask)
    

    Representative CPU codegen shape
    C++/OpenMP conceptual output
    #pragma omp parallel for
for (int64_t i = 0; i < rows; ++i) {
  for (int64_t j = 0; j < cols; ++j) {
    float v = mm[i * cols + j] + bias[j];
    out[i * cols + j] = std::max(v, 0.0f) * scale;
  }
}
    Lowering need not expand everything. Preserve high-level matmul for a tuned GEMM while lowering only the fusible epilogue to loops. Mixed abstraction levels are a practical strength.

    The GPU machine model you need
    Think massive parallelism, grouped execution, a memory hierarchy, and finite on-chip resources—not a mythical “fast device.”
    

    GPU DEVICE
    Many streaming multiprocessors
    SM 0SM 1SM 2SM 3…SM N
    A grid of thread blocks/program instances is scheduled across SMs. Blocks should be independent enough to run in any order.
    INSIDE ONE SM
    Warps share resources
    On NVIDIA GPUs, execution is grouped into 32-lane warps. Divergent branches may serialize paths inside a warp.
    

    fastestregistersper-lane values
    fastshared memoryon-chip, block scope
    cachedL1 / L2hardware-managed reuse
    largestglobal memoryHBM/DRAM, high latency
    

    DecisionGood outcomeFailure mode
    TilingA program handles a reusable block.Too small: overhead; too large: resource pressure.
    CoalescingNeighbor lanes access neighbor addresses.Scattered accesses require more transactions.
    StagingReuse from shared memory/registers.Copies and barriers outweigh reuse.
    ReductionTree/warp combine partials efficiently.Serial chain or heavy atomics.
    OccupancyEnough warps hide latency.Registers/shared memory limit active blocks.
    

    Roofline intuition
    MEMORY-BOUND
    Low arithmetic intensity
    Few operations per byte. Pointwise chains fit here; fusion helps by avoiding intermediate traffic.
    COMPUTE-BOUND
    High arithmetic intensity
    Many operations per byte. GEMM fits here; tile reuse and tensor-core schedules dominate.
    Measure before tuning. Inspect kernel duration, launch gaps, achieved bandwidth, occupancy, and tensor-core eligibility. “GPU utilization” alone is not a diagnosis.
    

    09
    Triton: blocked programs, not scalar threads
    Triton describes blocks of tensor work. Its compiler maps a block program onto lower-level GPU execution.
    

    A complete vector-add kernel
    vector_add.py · annotated
    import torch, triton
import triton.language as tl

@triton.jit
def vector_add_kernel(x_ptr, y_ptr, out_ptr,
                      n: tl.constexpr, BLOCK: tl.constexpr):
    program = tl.program_id(axis=0)  # block-program ID
    offsets = program * BLOCK + tl.arange(0, BLOCK)
    valid = offsets < n             # tail mask
    x = tl.load(x_ptr + offsets, mask=valid, other=0.0)
    y = tl.load(y_ptr + offsets, mask=valid, other=0.0)
    tl.store(out_ptr + offsets, x + y, mask=valid)

def vector_add(x, y):
    out = torch.empty_like(x)
    n = x.numel()
    grid = (triton.cdiv(n, 256),)
    vector_add_kernel[grid](x, y, out, n=n, BLOCK=256)
    return out
    

    Choose a program instance
    program_id(0) identifies a block program in a 1-D grid.
    Create a block of indices
    arange gives vector offsets. Think tiles, not individual thread IDs.
    Mask the tail
    The final program must not touch addresses beyond n.
    Load, compute, store
    Vector-shaped operations are distributed to GPU lanes during lowering.
    Launch enough programs
    ceil_div(n,BLOCK) covers the vector exactly once.
    

    Add a reduction: row softmax
    row_softmax skeleton
    @triton.jit
def row_softmax(x_ptr, out_ptr, cols: tl.constexpr,
                BLOCK: tl.constexpr):
    row = tl.program_id(0)
    col = tl.arange(0, BLOCK)
    mask = col < cols
    x = tl.load(x_ptr + row * cols + col,
                mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)
    numer = tl.exp(x)
    denom = tl.sum(numer, axis=0)
    tl.store(out_ptr + row * cols + col,
             numer / denom, mask=mask)
    One program owns one row. Rounding the block to a power of two simplifies reduction but wastes work for awkward widths. Larger rows may require multi-stage reduction.

    10
    torch.compile versus torch.export
    One optimizes execution inside Python. The other captures an explicit program and constraints for downstream tooling and deployment.
    

    TORCH.COMPILE
    JIT optimization
    • Python remains runtime
    • Graph breaks allowed by default
    • Guarded specializations cached
    • First choice for speed
    TORCH.EXPORT
    AOT capture boundary
    • Produces ExportedProgram
    • Explicit ATen graph + signature
    • Shape constraints recorded
    • Useful for deployment/tooling
    

    Export with dynamic batch
    export_lab.py
    import torch
from torch.export import Dim, export

class InferenceBlock(torch.nn.Module):
    def forward(self, x, w, bias):
        return torch.relu(x @ w + bias)

model = InferenceBlock().eval()
x = torch.randn(8,128)
w = torch.randn(128,256)
b = torch.randn(256)
batch = Dim("batch", min=1, max=64)

ep = export(model, (x,w,b),
            dynamic_shapes=({0: batch}, None, None))
print(ep.graph_module.graph)
print(ep.graph_signature)
print(ep.range_constraints)
    

    Export is stricter because arbitrary Python cannot conveniently resume at deployment. Unsupported Python, data-dependent shapes, mutations, custom ops without metadata, and incomplete constraints become explicit problems.
    Rule: use torch.compile when Python remains and you want speed. Use torch.export when another system needs a captured program with a declared contract.

    Benchmark correctly
    Verify parity
    torch.testing.assert_close with dtype-appropriate tolerance.
    Separate compile time
    Warm up; first call captures and compiles.
    Synchronize CUDA
    Use events or controlled synchronization around asynchronous work.
    Use real shape distributions
    Not one friendly power-of-two input.
    Profile the winner
    Confirm the mechanism: fewer launches, traffic, or better kernels.
    

    Common failure modes
    Compilation is slower
    Compile cost may dominate; breaks may create tiny regions; input may be too small; dynamic shapes may recompile; fusion may hurt occupancy; or another pipeline stage is the bottleneck. Measure warm steady state.
    It recompiles on every request
    Look for changing scalars, module attributes, train/eval mode, dtype/device, rank, stride, or shapes. Read the guard-failure line before changing configuration.
    A custom op breaks the graph
    Register a schema and fake/meta implementation that calculates output metadata without running the kernel. Declare mutation/alias behavior and autograd correctly.
    Eager and compiled outputs differ
    Reduce the reproducer, freeze randomness, walk backend rungs, inspect mutation/aliasing, compare intermediates, and check dtype/fast-math sensitivity. Do not hide a bug by widening tolerance blindly.
    Export constraints fail
    The program may impose relations missing from your dynamic-shape declaration. Decide whether suggested constraints match the real deployment contract.
