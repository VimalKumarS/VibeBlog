MetricFlow — a TSDB for an observability platform

We're designing MetricFlow: ingesting 50M data points/sec from 10K hosts and 200 microservices, storing 24h hot in memory + 365 days cold on disk, serving sub-100ms queries to 5K dashboards and 50K alerts — at $0.0001 per million points.

Chapter 1

Why time-series
needs its own database.

Time-series data is fundamentally different from relational rows. Every record has a timestamp. Writes are append-mostly. Reads are range-scans over time windows. Cardinality explodes by metric × tag combinations. A relational database isn't designed for any of this.

A general-purpose database stores rows independently. A TSDB stores points belonging to the same time series contiguously — same metric name + same tags = same physical chunk. This single decision is what enables 10×+ compression, 100×+ query speed, and ingest rates measured in tens of millions of points per second per node.

tsdb vs relational db — same workload, vastly different shapes showing: relational
📈

Append-mostly writes

99% of writes are new points at the latest timestamp. Almost no updates, almost no deletes. Storage engines optimised for this pattern (LSM trees, columnar formats) outperform B-trees by orders of magnitude.

🔢

High cardinality

1 metric × 200 services × 10K hosts × 50 tags = 100M time series. Each is a logical "row". Cardinality is the #1 enemy of every TSDB. Tag-explosion is what kills observability budgets.

⏱️

Range-scan queries

"Show p99 latency of payment-service for the last 1 hour" → scan all points in a time range, group by tags, aggregate. Not a point lookup. Index by (metric, tag) combinations + time.

🗜️

Compression-friendly

Sequential timestamps differ by predictable intervals. Sequential values are similar. XOR + delta-of-delta encoding (Gorilla) achieves 1.4 bytes/point on real-world data — 10× better than naïve formats.

Chapter 2

The data model —
metric, tags, points.

A time series in MetricFlow (and Goku, OpenTSDB, Prometheus) is identified by a metric name and a set of tag key=value pairs. Every data point in that series is a (timestamp, value) tuple. The cardinality of metric × tags determines everything about cost and performance.

# A single time series in MetricFlow metric: "http.server.duration" tags: {service="payment-api", host="prod-01", region="us-east-1", status="200"} points: [ (1735000000, 42.3), # Wed Dec 24 00:00:00 UTC 2024 → 42.3 ms (1735000060, 41.8), # 60 seconds later → 41.8 ms (1735000120, 43.1), # … ] # The series identifier (used for sharding and indexing) series_id = hash("http.server.duration|host=prod-01|region=us-east-1|service=payment-api|status=200") # tags sorted alphabetically for canonical form
cardinality = unique combinations of (metric × tag values)
Cardinality math for MetricFlow:
1 metric (http.server.duration) × 200 services × 10K hosts × 4 regions × 5 status codes = 40M unique series for one metric.
Multiply by 5K metrics across the platform = 200B time series. This is impossible — and the reason MetricFlow imposes a per-tag-value cap and rejects unbounded tags (user_id, request_id, trace_id) at ingest time.
Golden rule: tags must be of bounded cardinality (<1000 distinct values). High-cardinality identifiers belong in logs, not metrics.

What metrics are good for

  • Counters: requests served, errors, bytes sent
  • Gauges: CPU%, memory used, queue depth, active connections
  • Histograms: request latency, payload size distribution
  • Aggregated business metrics: orders/min, revenue by region
  • Dimensions: service, host, region, status_code, environment

What metrics are NOT for

  • Per-user metrics (user_id as tag = cardinality bomb)
  • Per-request metrics (use traces/exemplars instead)
  • Free-form text fields (use logs)
  • Audit trails (use append-only event store)
  • Anything where you need exact-record retrieval
Chapter 3

The complete
architecture — like Goku.

MetricFlow follows the Goku reference architecture: a hot in-memory tier (24h), a long-term tier on RocksDB (365d), a compactor that rolls up and re-shards, and a query routing layer that fans out to the right tier. Everything sharded, everything replicated.

complete architecture — click any component click to explore
📡

Metric Agents

One per host. Collects system + app metrics every 10s. Buffers locally, flushes to Kafka. Can survive Kafka outage (24h local buffer). Stateless beyond local buffer.

📨

Kafka Ingest

Topic per metric namespace. Partitioned by series_id hash. Acts as durable buffer + decouples agents from storage. 7-day retention as disaster recovery.

⚡

Hot Tier (MFs)

"MetricFlow Short-term". In-memory storage for last 24h. Gorilla compression. 2-hour BucketMap shards. Zero-disk reads on hot queries. Replicated 2× for HA.

💾

Cold Tier (MFl)

"MetricFlow Long-term". RocksDB-backed. Tiered SSTables. Stores 365 days. Reads from S3-archived SSTs for very old data. Fan-out queries on disk.

🔄

Compactor

Reads finalized buckets from S3. Rolls up to 1m → 5m → 1h granularity. Re-shards for cold tier. Writes SSTables back to S3 for ingestion by MFl.

🚦

Query Root

Routes queries to MFs (recent) or MFl (historic). Fans out to all relevant shards. Aggregates partial results. Returns to client. Stateless. Behind a load balancer.

Chapter 4

Ingest path —
from metric agent
to memory.

A point's journey: agent collects → buffers locally → batches to Kafka → ingestion service consumes → routes to correct shard → writes to in-memory bucket → asynchronously persists to durable storage. Every hop optimised for throughput, not latency.

ingest pipeline — step through each phase step 1 of 7

Sharding strategy

consistent hash ring — point routing across shards drag a point
shard = hash(series_id) % num_shards
Why hash by series_id, not by timestamp: hashing by series_id keeps all points of a series on the same shard. Range queries on a single series hit one shard. Hashing by timestamp would scatter a series across all shards — every query becomes a fan-out to all nodes. Catastrophic at scale.
Why consistent hashing: when adding/removing a shard, only ~1/N of series move. Naïve modulo would relocate everything. Goku uses Apache Helix for cluster topology and rebalancing.
// Ingest worker — Kafka consumer → in-memory bucket write while (true) { vector<DataPoint> batch = kafka.poll(100); // 100 ms timeout for (auto& point : batch) { // Route to shard u32 series_id = hash_series(point.metric, point.tags); u32 shard_id = consistent_hash(series_id, ring); if (shard_id != THIS_NODE_ID) { forward_to_peer(shard_id, point); // rare — agent should hit right shard continue; } // Determine 2-hour bucket u64 bucket_ts = point.timestamp - (point.timestamp % 7200); Bucket* bucket = bucket_map.get_or_create(series_id, bucket_ts); // Append to Gorilla-encoded stream (1.4 bytes/point) bucket->append_gorilla(point.timestamp, point.value); // Async log to S3 for durability wal.append(point); } kafka.commit(); }
Chapter 5

The hot tier —
BucketMap + Gorilla
in memory.

The hot tier holds the most recent 24 hours entirely in RAM, organised as a BucketMap: a hash map from series_id to a list of 2-hour buckets, each containing a Gorilla-compressed stream of points. This is where 95% of queries land.

BucketMap structure — series → 2-hour buckets click a bucket

Gorilla compression — the magic 1.4 bytes/point

gorilla encoding — XOR + delta-of-delta naïve: 16 bytes · gorilla: 1.4 bytes

Timestamp delta-of-delta encoding

  • Most metrics arrive at fixed intervals (10s, 60s).
  • Delta from prior timestamp is constant → encode as 0 bits.
  • Δ from delta = 0 → 1 bit (variable-length prefix).
  • Result: typical timestamp encodes in ~2 bits instead of 64.
  • An hour of 10s-interval points: 360 timestamps × 2 bits = 90 bytes. (vs 360 × 8 = 2.88 KB naïve.)

Value XOR encoding

  • Successive metric values are often similar (CPU%, latency).
  • XOR previous value with current → most bits are 0.
  • Encode the leading-zeros + meaningful-bits + trailing-zeros.
  • Constant value → 1 bit. Slightly different value → 10–20 bits.
  • Result: typical value encodes in ~10 bits instead of 64.
// Gorilla compression — combined timestamp + value encoding struct GorillaStream { BitWriter bits; u64 last_ts = 0; i64 last_delta = 0; f64 last_value = 0; void append(u64 ts, f64 val) { // First point: write full ts + value if (last_ts == 0) { bits.write(ts, 64); bits.write(val, 64); last_ts = ts; last_value = val; return; } // Timestamp: delta-of-delta i64 delta = ts - last_ts; i64 dod = delta - last_delta; if (dod == 0) bits.write_bits("0", 1); // 1 bit else if (dod >= -63 && dod <= 64) bits.write_bits("10" + zigzag7(dod), 9); else if (dod >= -255 && dod <= 256) bits.write_bits("110" + zigzag9(dod), 12); else bits.write_bits("1110"+ zigzag32(dod),36); // Value: XOR with previous u64 xor_val = to_bits(val) ^ to_bits(last_value); if (xor_val == 0) { bits.write_bits("0", 1); // repeat — 1 bit! } else { bits.write_bits("1" + encode_xor(xor_val), variable); } last_ts = ts; last_delta = delta; last_value = val; } };
Real-world compression ratios: production Goku reports 1.37 bytes/point average across all Pinterest metrics. Compare to: naïve binary 16 bytes (12× savings), Prometheus chunk format ~3 bytes (2× savings), JSON ~30 bytes (22× savings). At 50M points/sec ingest, this is 70 MB/sec saved versus naïve — an entire 10 GbE link.
Chapter 6

The cold tier —
RocksDB + tiered
SSTables.

After 24 hours, hot data graduates to the cold tier — RocksDB-backed, organised as tiered SSTables (Static Sorted Tables). Smaller recent SSTs in lower tiers, larger older SSTs in higher tiers. The compactor merges across tiers as data ages.

tiered LSM SSTable structure — watch compaction over time L0: 0 files
📥

L0: recent flushes

Memtable flushes write here. Multiple SSTs may overlap in key range. Reads must check all of them. Triggers compaction when count exceeds threshold.

🔀

L1–L6: sorted tiers

Each level 10× larger than previous. Within a level, SSTs have non-overlapping key ranges. Read at most 1 SST per level. Predictable read amplification.

📊

Bloom filters

Each SST has a Bloom filter for its keys. Skip SSTs that don't contain the queried series. Reduces I/O by 10× for sparse queries. ~10 bits/key, 1% false positive rate.

📚

Block cache

Hot SST blocks cached in memory (LRU). Recent queries return from cache without disk I/O. Sized to ~30% of node RAM.

Chapter 7

Query path —
scatter, partial-aggregate,
gather.

A query "p99 latency of payment-service over last 1 hour, grouped by region" must touch every shard holding matching series. The query root fans out, each shard computes a partial aggregate, the root merges. Critical optimization: push computation to leaves, not data to the root.

scatter-gather query execution — watch the lifecycle click "run query"
Shards 4
partial aggregation at leaves + final aggregation at root
The killer optimization: instead of returning 10M raw points to the root and aggregating there, each leaf shard computes its own partial p99 (say from 1M points → 1 number), and the root aggregates 4 partial p99s into a global p99. Network I/O drops from 10M points (160 MB) to 4 numbers (32 bytes). Query time goes from 30s to 80ms.
Aggregator decomposability: sum, count, min, max are perfectly decomposable. Average decomposes to (sum, count). Percentiles use t-digests (mergeable sketches). Standard deviation uses Welford's online algorithm. Some aggregators (e.g. exact median) are NOT decomposable — TSDBs avoid these.

Scatter — fanout in parallel vector<future<PartialResult>> futures; for (auto shard : shards) { futures.push_back(async([=]{ return shard.compute_partial(q); // runs at leaf })); } // 3. Gather + merge partial results Aggregator root_agg(q.aggregator); for (auto& f : futures) { root_agg.merge(f.get()); // e.g. merge t-digests for p99 } return root_agg.finalize(); }
Chapter 8

The compactor —
rollups, re-sharding,
downsampling.

Raw 10-second points × 365 days = 3.15M points per series. For a metric with 100M series, that's 315B points stored at full resolution. The compactor solves this by rolling up: 10s → 1m → 5m → 1h granularity as data ages. Older data, less precise, vastly less storage.

rollup pipeline — full resolution to multi-tier rollups step through

Storage savings from rollups

  • 10s resolution: 360 points/hour × 24 = 8,640/day
  • 1m rollup: 60/hour × 24 = 1,440/day (6× less)
  • 5m rollup: 12/hour × 24 = 288/day (30× less)
  • 1h rollup: 24/day (360× less)
  • Combined retention: 1d raw + 30d 1m + 6m 5m + 5y 1h
  • Total storage: ~50× less than full-resolution 5-year retention

Rollup aggregations stored

  • For each rollup window: count, sum, min, max
  • For percentile metrics: t-digest sketch (~5KB per series per window)
  • Allows recomputing any aggregator at query time without raw data
  • p99 over 30 days = merge t-digests, finalise
  • avg = sum / count (always recomputable)

Capacity numbers

Hot tier RAM50M points/sec × 1.4 bytes × 86400 sec = 6 TB/day raw in memory. With 2× replication = 12 TB. Across 150 nodes × 80 GB = 12 TB. matches Goku
Hot tier nodes~150 nodes × 128 GB RAM each (80 GB for time series, 48 GB for OS/cache/headroom). r5.4xlarge or equivalent.
Cold tier disk365 days, multi-tier rollups. Raw 1d + 1m 30d + 5m 6m + 1h 5y = ~150 TB compressed total. NVMe SSD tier (last 30d) + S3-backed (older).
Kafka throughput50M points/sec × 32 bytes (uncompressed wire format) = 1.6 GB/sec ingest. ~30 brokers, 3 racks. 7-day retention = 1 PB Kafka storage.
CompactorReads 6 TB/day from hot, computes rollups, writes ~600 GB/day rolled up to cold. Sustained throughput target: 70 MB/sec read, 7 MB/sec write per shard. Spark or custom workers.
Query QPS10K dashboards × 60 panel-seconds avg + 50K alerts × 1 query/min = ~5K QPS. p99 query latency target: 500ms. p99.9 target: 2s.
Total cost~$200K/month all-in (compute + storage + network) for this scale. Pinterest reports 70% cost reduction post-2024 optimisations on similar load.

What breaks at next scale level

💥

Cardinality explosion

One bad metric with user_id in tags = 100M new series in a day. Indexes blow up. RAM exhausted. Detect with cardinality monitor, reject at ingest.

🐌

Hot shard / hot key

One series hammered by all queries (e.g. global p99). Single shard gets 100× load. Mitigate with read-replicas for the shard, or pre-aggregate via continuous query.

🔥

Bucket boundary spike

Every 2 hours, all hot buckets close, 6 TB flushes to S3 at once. Network saturates. Stagger bucket boundaries across shards to spread load.

🌐

Multi-region writes

Globally distributed agents writing to a single TSDB cluster = high WAN latency. Solve with regional clusters + cross-region read federation, or Kafka MirrorMaker.

The one-sentence mental model: A Goku-class TSDB shards time series by series_id hash, holds the last 24h in memory using Gorilla-compressed 2-hour buckets, persists older data to RocksDB tiered SSTables on disk and S3, runs a compactor that builds multi-resolution rollups for cheap long-term storage, and answers queries via scatter-gather with partial aggregation pushed to leaf shards — handling 50M points/sec ingest and millisecond queries on petabyte-scale historic data.
