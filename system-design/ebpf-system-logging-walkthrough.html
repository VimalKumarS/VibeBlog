Chapter 1

What eBPF is —
and why it changes
everything.

eBPF lets you run sandboxed programs inside the Linux kernel — without recompiling the kernel, loading kernel modules, or modifying application code. It's the safest way to observe, trace, and log everything a system does, at every layer.

Before eBPF, kernel instrumentation meant: recompile the kernel (days), load a kernel module (risk system crash), use strace (25× overhead), or add application-level logging (requires code changes across every service). eBPF does all of this with <1% overhead, dynamically at runtime, for any running process.

eBPF = JIT-compiled bytecode + verifier + kernel hooks
🔒

Safe by design

The eBPF verifier statically analyses every program before loading. No infinite loops, no null pointer dereferences, no out-of-bounds access. A buggy eBPF program is rejected — it cannot crash the kernel.

⚡

JIT compiled

eBPF bytecode is JIT-compiled to native machine code at load time. Runs at native speed inside the kernel — no interpretation overhead. p50 execution: 100–500 nanoseconds per event.

🔌

No app changes

Attach to any running process without restarting it. Instrument a production service you don't own, in a language you don't control, with zero deployment. The application never knows it's being traced.

🌐

Any kernel event

System calls, function entry/exit, network packets, file I/O, scheduler events, memory allocation, hardware performance counters. If the kernel does it, eBPF can observe it.

📦

Portable (CO-RE)

Compile Once – Run Everywhere. BTF (BPF Type Format) encodes kernel struct layouts. eBPF programs adapt to kernel version differences at load time — one binary, every kernel.

🗺️

Bidirectional

eBPF programs communicate with userspace via BPF maps. Push events to userspace via ring buffers. Pull configuration from userspace. Full bidirectional data channel.

Chapter 2

How eBPF programs
enter the kernel.

An eBPF program goes through a strict lifecycle: write in C (or Rust), compile to BPF bytecode, load via syscall, pass the verifier, JIT compile to native code, attach to a kernel hook, run on every matching event.

eBPF lifecycle — from C source to kernel execution step 1 of 6
verifier — watch it check a program for safety verifying…

Verifier checks

  • No unbounded loops (bounded iteration only, since 5.3)
  • No null pointer dereferences — every pointer must be range-checked
  • No out-of-bounds memory access
  • All code paths must terminate
  • Stack size ≤ 512 bytes
  • Function call depth ≤ 8 (tail calls extend this)
  • Map accesses through proper helpers only

JIT compilation targets

  • x86_64 — Intel/AMD, the primary target
  • ARM64 — Raspberry Pi, mobile, Apple Silicon VMs
  • s390x — IBM mainframes
  • RISC-V — emerging embedded
  • JIT disabled: falls back to interpreted mode (slower)
  • Check: cat /proc/sys/net/core/bpf_jit_enable

BPF maps —
the data channel
between kernel and user.

BPF maps are kernel data structures shared between eBPF programs and userspace processes. They are the only way for an eBPF program to store persistent data or communicate with userspace. Choose the right map type — it's the most important performance decision.

Chapter 4

Hook points —
where eBPF attaches
in the kernel.

eBPF programs attach to specific kernel events. The choice of hook point determines what you can observe, the data available, and the overhead. For system logging, tracepoints and kprobes are the primary tools.

kernel hook points — click any to explore its capabilities click a hook

tracepoints — stable ABI

  • Static instrumentation points in the kernel source.
  • Stable across kernel versions — ABI guaranteed.
  • Available events: ls /sys/kernel/debug/tracing/events/
  • Examples: syscalls/sys_enter_openat, sched/sched_process_exec
  • Preferred over kprobes when available — more stable.

kprobes — any kernel function

  • Dynamic instrumentation of any kernel function.
  • kprobe: entry of function. kretprobe: return of function.
  • Can break on kernel version changes if function signatures change.
  • More powerful than tracepoints — access to all arguments.
  • Use CO-RE + BTF to handle struct layout differences across kernels.

System logging with eBPF —
file, network, process.

eBPF-based system logging captures what application-level logs cannot: every file access, every network connection, every process spawn — without instrumenting the application. This is the foundation of runtime security monitoring and deep observability.

Complete eBPF program — file access logger

// File access logger — traces openat() syscall for every process #include "vmlinux.h" #include <bpf/bpf_helpers.h> #include <bpf/bpf_core_read.h> struct file_event { u32 pid; u32 uid; char comm[16]; /* process name */ char filename[256]; int flags; /* O_RDONLY, O_WRONLY, O_CREAT … */ u64 timestamp_ns; }; /* Ring buffer — lock-free, highest throughput */ struct { __uint(type, BPF_MAP_TYPE_RINGBUF); __uint(max_entries, 1 << 20); /* 1 MB */ } rb SEC(".maps"); SEC("tracepoint/syscalls/sys_enter_openat") int trace_openat(struct trace_event_raw_sys_enter *ctx) { struct file_event *e; u64 id = bpf_get_current_pid_tgid(); /* Reserve space in ring buffer — zero-copy */ e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0); if (!e) return 0; /* ring full — drop (counted) */ e->pid = id >> 32; e->uid = bpf_get_current_uid_gid() & 0xffffffff; e->timestamp_ns = bpf_ktime_get_ns(); e->flags = (int)ctx->args[2]; bpf_get_current_comm(&e->comm, sizeof(e->comm)); bpf_probe_read_user_str(e->filename, sizeof(e->filename), (const char *)ctx->args[1]); bpf_ringbuf_submit(e, 0); /* make visible to userspace */ return 0; }
Why ring buffer over perf event array: BPF_MAP_TYPE_RINGBUF (kernel 5.8+) is lock-free, memory-efficient, and preserves event ordering. A single ring buffer is shared across all CPUs. perf_event_array has one buffer per CPU — consuming events from multiple CPUs requires multiple polling threads and complex ordering logic.
Chapter 6

eBPF + OpenTelemetry —
kernel events as spans.

The killer combination: eBPF captures kernel events with zero overhead, OpenTelemetry carries them as structured traces and metrics to any backend. Together they give you application-level context (trace_id, span_id) attached to kernel-level events (file opens, network connects).

eBPF → OTel correlation — syscall event becomes a span with trace_id idle

How correlation works

  • OTel SDK writes current trace_id into a well-known memory location (thread-local storage).
  • eBPF program reads that memory location via bpf_probe_read_user().
  • Kernel event now carries the trace_id — it can be correlated with the OTel trace in Tempo/Jaeger.
  • Grafana exemplar: metric spike → trace_id → eBPF-captured syscall events in that trace.

Chapter 7

Security logging —
runtime threat detection.

eBPF is the foundation of modern container security. Tetragon (by Cilium), Falco, and Tracee use eBPF to capture kernel events and detect threats in real time — privilege escalation, unexpected file access, container escapes — without agents inside containers.

threat detection scenarios — click to simulate system clean

What eBPF detects that nothing else can

  • Execution of setuid binaries inside containers
  • Unexpected capability acquisition (CAP_SYS_ADMIN)
  • Sensitive file access: /etc/shadow, /proc/kallsyms
  • Container namespace escape via unshare/nsenter
  • Unexpected outbound network connections
  • Memory injection via ptrace or /proc/pid/mem
  • DNS resolution to known C2 domains
  • Binary replacement (writing to /usr/bin/*)

Tetragon enforcement policy

  • Tetragon goes beyond detection — it can enforce policy via eBPF.
  • A TracingPolicy can kill a process at the syscall boundary — before the syscall completes.
  • Example: block any write to /etc/passwd in real time, not after the fact.
  • This is eBPF's unique advantage over audit logging: prevention, not just detection.
// Tetragon policy — detect and kill privilege escalation attempts apiVersion: cilium.io/v1alpha1 kind: TracingPolicy metadata: {name: block-setuid-exec} spec: kprobes: - call: "sys_execve" syscall: true selectors: - matchCapabilities: - type: Effective operator: In values: ["CAP_SETUID"] matchNamespaces: - namespace: Pid operator: NotIn values: ["host_ns"] # only inside containers matchActions: - action: Sigkill # kill the process — enforcement!

The one-sentence mental model: eBPF runs a verified, JIT-compiled bytecode program inside the Linux kernel at a hook point — tracepoint, kprobe, or XDP — captures event data into a shared ring buffer map, which userspace reads via poll, converts to OTel spans with the kernel-extracted trace_id, and ships to Prometheus/Tempo/Grafana for correlation — all with <1% overhead, zero application changes, and complete kernel-level visibility.
