Chapter 1

Why production models
silently degrade.

A model trained today is already decaying. The world it was trained on is not the world it will serve tomorrow. ML model monitoring is the discipline of detecting that decay before it becomes a business incident.

Unlike software bugs — which fail loudly with errors and stack traces — ML model degradation is silent. Accuracy drops by 3% per week. No exception is thrown. No red deployment indicator. Users just get slightly worse predictions, quietly, until someone notices the business metric moved.

Monitoring gap = time_to_detect − time_of_degradation
📉

Silent accuracy loss

The model still returns predictions. No errors. But p(correct) drops 2% per week as the world changes. Users lose trust. No alert fires.

🌍

World changes constantly

User behaviour evolves. New products launch. Competitors enter. Regulations change. Sensors drift. The model was trained on yesterday's world.

💸

Business impact

A fraud model's TPR drops from 85% → 70%: $2M/week more fraud passes through. A recommendation model's CTR drops 1.5%: $40M/year revenue impact.

⚡

Early detection = cheap fix

Detecting drift early means a lightweight fine-tune or feature update. Detecting late means a full retraining cycle: data collection, labelling, training, validation, deployment. 10× more expensive.

Root causes of production degradation: data drift (input distribution shifts) · concept drift (relationship between input and output changes) · label drift (target distribution shifts) · upstream data quality issues · schema changes in upstream pipelines · feature store staleness · feedback loop corruption.
Chapter 2

Three types of drift —
data, concept, label.

Not all drift is the same. Data drift changes your inputs. Concept drift changes the relationship your model learned. Label drift changes what you're even predicting. Each requires a different detection strategy.

drift types — click each to visualise what changes data drift

Sudden vs gradual drift

  • Sudden: A data pipeline bug, a new product launch, COVID lockdowns. Distribution changes overnight. Easy to detect with statistical tests.
  • Gradual: Seasonal patterns, slow user behaviour evolution, sensor aging. Distribution shifts over weeks/months. Harder to detect — requires rolling baselines.
  • Recurring: Weekly patterns, quarterly cycles. Normal variability — need to distinguish from true drift.

Upstream vs downstream detection

  • Upstream (input): Monitor feature distributions before prediction. Can detect drift without ground truth labels. Faster signal.
  • Downstream (output): Monitor prediction distribution shift. Also fast, no labels needed.
  • Ground truth (outcome): Requires actual labels from production. Delayed — days to weeks for labelled feedback. The most accurate signal.
Chapter 3

Statistical tests —
PSI, KS, KL, chi-squared.

Every drift detector is a statistical test comparing a reference distribution (training data) to a production distribution (live data). The choice of test depends on your data type and what sensitivity you need.

When to use which test

PSICategorical / binned continuous. Classic in finance. Thresholds: <0.1 stable · 0.1–0.25 warning · >0.25 alert. Simple, interpretable, widely understood. recommended for tabular ML
KS testContinuous features. Compares CDFs. Returns p-value and D-statistic. Alert when p < 0.05. best for continuous distributions
KL divergenceProbabilistic, asymmetric. Sensitive to zero bins (add smoothing). Unbounded — hard to threshold. Good for output probability distributions. use with care
Chi-squaredCategorical features. Tests whether two categorical distributions are the same. Classic hypothesis test with p-value. best for categoricals
JS divergenceSymmetric version of KL. Bounded [0,1]. No zero-bin sensitivity. Better than KL for most use cases. 0 = identical · 1 = completely different. preferred over KL
Wasserstein distanceEarth mover's distance. Robust to outliers. Captures shape of distribution shift. Computationally heavier. for high-dimensional embeddings
# PSI calculation — production-grade implementation import numpy as np def compute_psi(reference, production, bins=10): """PSI < 0.1 stable · 0.1-0.25 warn · > 0.25 alert""" ref_pct, edges = np.histogram(reference, bins=bins, density=True) prod_pct, _ = np.histogram(production, bins=edges, density=True) # Avoid log(0) with small epsilon ref_pct = np.where(ref_pct == 0, 1e-4, ref_pct) prod_pct = np.where(prod_pct == 0, 1e-4, prod_pct) psi = np.sum((prod_pct - ref_pct) * np.log(prod_pct / ref_pct)) return psi # KS test for continuous features from scipy.stats import ks_2samp stat, p_value = ks_2samp(reference_data, production_data) if p_value < 0.05: alert(f"KS drift detected: stat={stat:.3f}, p={p_value:.4f}")
Chapter 4

Performance monitoring —
metrics, slices,
and the label delay problem.

Accuracy, AUC, F1, precision, recall — these are the metrics that matter most, but they require ground truth labels. The label delay problem is the hardest challenge in production ML monitoring.

performance metrics live simulation — watch degradation across segments all healthy
Slice level aggregate

The label delay problem

  • You make a prediction today. Ground truth arrives in 1–90 days (fraud: days, medical: weeks, churn: months).
  • By the time you know your model was wrong, thousands more predictions were made with the same broken model.
  • Proxies: use upstream data drift as an early warning, before labels arrive.
  • Proxy labels: use business events as pseudo-labels (click, purchase, complaint) when direct labels are delayed.

Slice-level monitoring

  • Aggregate metrics hide sub-group failures. Simpson's paradox: overall accuracy can improve while accuracy for a specific demographic drops sharply.
  • Required slices: region, age group, device type, feature value quantile, new vs returning user.
  • Alert when: slice metric deviates more than 3σ from its own baseline, OR slice metric diverges from overall metric by more than N%.
  • Minimum slice size: 100–500 samples before alerting (statistical significance).

# Slice-level performance monitoring import pandas as pd from sklearn.metrics import roc_auc_score def monitor_slices(df, slice_cols, target, score_col): results = {} # Overall baseline results['overall'] = roc_auc_score(df[target], df[score_col]) for col in slice_cols: for val in df[col].unique(): slice_df = df[df[col] == val] if len(slice_df) < 100: # min sample size continue auc = roc_auc_score(slice_df[target], slice_df[score_col]) results[f'{col}={val}'] = auc # Alert if slice diverges > 5% from overall if abs(auc - results['overall']) > 0.05: alert(f"Slice {col}={val}: AUC {auc:.3f} vs overall {results['overall']:.3f}") return results
Chapter 5

Infrastructure monitoring —
latency, throughput,
and serving health.

Model accuracy monitoring is only half the story. A model can be statistically healthy but serving users with 10-second latency, crashing under load, or silently returning stale predictions from a cache. Infrastructure monitoring catches these failures.

inference latency distribution — p50 / p95 / p99 live tracking p99: 42ms
Load (req/s) 100
⏱️

Inference latency

p50 (median), p95, p99. SLO: p99 < 200ms for real-time models. Tail latency kills user experience. Track per model version — rollback if p99 regresses.

📈

Throughput

Requests per second actually served vs requested. Drop in throughput with same load = degradation (OOM, GC pause, model re-load). Track per endpoint, per model version.

❌

Error rate

HTTP 5xx rate, model-level errors (deserialization failure, OOM kill, timeout). Alert: error rate > 1% sustained for 2 minutes. Separate model errors from infra errors.

🧠

Resource saturation

CPU / GPU utilisation, memory RSS, GPU VRAM, disk I/O. A model running at 95% GPU utilisation has no headroom for load spikes. Alert at 80% sustained.

🔢

Prediction volume

Sudden drop = upstream service failure or feature pipeline outage. Sudden spike = traffic anomaly or attack. Both are as important as accuracy.

📦

Batch staleness

For batch prediction systems: time since last successful batch run. If the batch job failed silently, users get 3-day-old predictions. Alert when staleness > 2× batch interval.

SLO error budget = 1 − target × time window
Define SLIs and SLOs for your model:
SLI: p99 inference latency · SLO: <200ms for 99.9% of requests over 30 days
SLI: prediction error rate · SLO: <0.5% over 1 hour
SLI: model AUC · SLO: >0.85 on weekly evaluation set
Error budget: 99.9% SLO = 43 min/month downtime budget. Burn rate alerts fire when you're consuming budget faster than sustainable.
Chapter 6

LLM monitoring —
a different beast.

Traditional ML monitoring measures numeric accuracy against ground truth labels. LLM monitoring is different: outputs are text, ground truth is often subjective, and new failure modes emerge — hallucination, toxicity, prompt injection, refusal rates, latency at token level.

LLM monitoring dimensions — click each to explore click a metric

LLM-specific metrics

  • Hallucination rate — % of outputs containing factually incorrect or fabricated content. Measured by NLI judge or retrieval grounding check.
  • Faithfulness — answer grounded in retrieved context. cosine(answer_embed, context_embed).
  • Answer relevancy — does the answer address the query? cosine(answer_embed, query_embed).
  • Toxicity / safety — % of outputs violating safety policies. Use classifier or LLM-as-judge.
  • Refusal rate — % of queries where model declined to answer. Spike = over-refusal regression.
  • Token throughput — tokens/second. Drops indicate GPU saturation or batching issues.

LLM evaluation patterns

  • Async judge sidecar — NLI or LLM judge runs off the critical path. No latency impact.
  • Reference-based eval — compare to known-good answers with BLEU, BERTScore, semantic similarity.
  • Reference-free eval — LLM-as-judge rates coherence, helpfulness, factuality. Scalable but circular.
  • Human evaluation — ground truth but expensive. Use for calibrating automated evals, not real-time.
  • Red-teaming logs — adversarial prompts that expose failure modes. Monitor prompt injection attempts.

Chapter 7

Fairness monitoring —
bias doesn't stay still.

A model that was fair at training time can become biased in production as data distributions shift differently across demographic groups. Fairness monitoring is a continuous obligation, not a one-time training-time check.

fairness metrics across demographic groups — watch bias emerge over time monitoring: all groups
Time period day 0

Fairness metrics

  • Demographic parity — P(ŷ=1 | group A) = P(ŷ=1 | group B). Equal positive prediction rates.
  • Equalized odds — equal TPR and FPR across groups.
  • Predictive parity — equal precision across groups. P(y=1 | ŷ=1) is same for all groups.
  • Individual fairness — similar individuals should receive similar predictions.
  • Note: these metrics are often mutually exclusive — you cannot satisfy all simultaneously (Chouldechova's impossibility theorem).

How production bias emerges

  • Training data drift is unequal across groups — Group A data drifts more than Group B.
  • Feature availability drops for specific groups (e.g. sparse data for rural users).
  • Feedback loops amplify existing decisions (hiring model learns from biased historical hires).
  • Proxy features — zip code correlated with race, credit score correlated with gender historically.
  • Alert: when TPR gap between any two protected groups exceeds 5%.

🔄

Retraining triggers

PSI > 0.25 sustained 24h · AUC drops >5% from baseline · Business KPI deviation >3σ · Scheduled (weekly, monthly). Champion-challenger: shadow model vs production.

🔙

Auto-rollback

Error rate > 5% for 5 min → automatic rollback to previous version. Latency p99 > SLO for 10 min → rollback. AUC drops > 10% on holdout set → block deployment.

🌓

Shadow mode

New model runs in parallel without affecting production traffic. Compare distributions of outputs. Measure business metrics side-by-side before promoting.

🧪

A/B testing

Split traffic: 90% control, 10% treatment. Measure business metrics (CTR, conversion, revenue) not just model metrics. Minimum detectable effect: 1%, sample size: N > 10k per arm.

Chapter 9

Five use cases —
different models,
different monitoring.

Every model type has a different failure mode, label delay, and monitoring strategy. Here's how to think about monitoring across the five most common production ML use cases.

use case monitoring comparison matrix

Tooling landscape

  • Evidently AI — open-source, data/model quality reports, drift tests, LLM evals. Best free option.
  • Arize AI / Fiddler — commercial, production-grade, built-in fairness, LLM support.
  • WhyLabs — real-time data and model monitoring, integrates with MLflow.
  • MLflow — experiment tracking + model registry. Monitoring via custom metrics.
  • Prometheus + Grafana — infrastructure metrics. Custom model metrics exported via OTel.
  • LangSmith / Langfuse — LLM-specific tracing, evaluation, and prompt management.

What to monitor — priority order

  • P0: Serving health (latency, error rate, volume) — always, real-time.
  • P1: Feature/prediction distribution drift — hourly PSI on key features.
  • P2: Slice-level business metrics — daily, on all protected attributes.
  • P3: Model accuracy metrics — as soon as labels arrive. Automate comparison to baseline.
  • P4: Fairness metrics — weekly or when P2 triggers.
  • P5: Downstream business KPIs — weekly business review.
The one-sentence mental model: ML model monitoring is a multi-layered early-warning system — data quality catches upstream pipeline failures, feature drift catches input distribution changes before labels arrive, prediction drift catches output changes immediately, performance metrics catch accuracy degradation when labels land, slice monitoring catches sub-group failures that aggregates hide, and infrastructure metrics catch serving failures independently of model quality.
