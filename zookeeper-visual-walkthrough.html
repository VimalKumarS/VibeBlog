Distributed coordination, step by step

How ZooKeeper keeps a cluster in agreement

Follow a write through quorum, crash the leader, watch a new one win—and then use ZooKeeper to elect the master of your own application.

There are two different “leaders”

ZooKeeper’s leader orders writes inside the ZooKeeper ensemble. Your application master is elected using znodes stored in ZooKeeper. They are separate roles and may run on different machines.

01 / MODEL

A tiny, replicated coordination filesystem

ZooKeeper stores small pieces of coordination data in a tree of znodes. Clients use that shared truth for membership, configuration, locks and leader election—not bulk application data.

Hierarchical znodes

Paths such as /services/api/node-01. Each node can hold small data and metadata.

Sessions + ephemeral nodes

An ephemeral znode disappears after its owner’s session expires—ideal for liveness.

Watches

A one-shot notification that tells a client to re-read after a znode changes.

Ordered updates

Every successful write gets a monotonic transaction id called a zxid.

Rule of thumbPut identities, leases, flags and pointers in ZooKeeper. Put logs, blobs and business records somewhere else.
02 / ENSEMBLE

Three servers, one logical service

An ensemble is usually an odd number of servers. A majority must be alive to make progress: 2 of 3, 3 of 5, and so on.

Why odd?Four voting servers still need 3 votes and tolerate only 1 failure—the same tolerance as 3 servers, but with more cost. Five servers tolerate 2 failures.
03 / TRAFFIC

Reads are local; writes become quorum decisions

ZooKeeper’s atomic broadcast protocol (ZAB) gives every healthy replica the same committed transaction order.

Write: set /config v2

1
Client contacts any serverA follower forwards the write to the ZooKeeper leader.
2
Leader creates a proposalThe proposal receives the next zxid and is broadcast.
3
Majority persists + ACKsLeader plus enough followers durably record it.
4
Commit is broadcastReplicas apply it in order; the client receives success.

Read: get /config

1
Client contacts one serverThe connected server can answer from its local in-memory tree.
2
No quorum round tripThis makes reads fast and scalable across followers.
3
Understand freshnessA server may be momentarily behind. Use sync() before a read when you need an up-to-date view.
4
Watch for changeRegister a watch, then re-read and re-register after it fires.
04 / FAILOVER

When the ZooKeeper leader disappears

The remaining voting members stop writes briefly, compare their histories, elect the best candidate, synchronize, and resume. Committed entries survive because a majority had already stored them.

T+0

Leader unavailable. TCP connections and heartbeats reveal the failure.

T+Δ

LOOKING state. Servers exchange votes during Fast Leader Election.

VOTE

Most up-to-date wins. Simplified priority: higher election epoch, then higher last zxid, then server id as tie-breaker.

SYNC

History aligns. The new leader brings followers to the same committed prefix.

READY

Broadcast resumes. Writes continue once a leader has quorum; clients reconnect automatically if configured correctly.

Safety invariant

  1. A write is successful only after a quorum records it.
  2. Any two quorums overlap in at least one server.
  3. Election favors the most complete history.
  4. Therefore a committed write is not replaced by an older history.
05 / APP MASTER

Elect your application master with ephemeral sequential znodes

Every process creates a unique numbered node. The smallest sequence owns leadership; everybody else watches only its immediate predecessor.

▾/my-service
▾/election
◆candidate-0000000012 ← smallest: MASTER
◆candidate-0000000013 ← watches 12
◆candidate-0000000014 ← watches 13

Application election simulator

P12 is master
Avoid the herd effectIf every follower watches the leader, one failure wakes all clients. Watching only the immediate predecessor wakes exactly the next candidate.

import org.apache.curator.framework.CuratorFramework;
import org.apache.curator.framework.CuratorFrameworkFactory;
import org.apache.curator.framework.recipes.leader.LeaderLatch;
import org.apache.curator.retry.ExponentialBackoffRetry;

public final class MasterProcess {
  public static void main(String[] args) throws Exception {
    CuratorFramework client = CuratorFrameworkFactory.newClient(
        "zk1:2181,zk2:2181,zk3:2181",
        new ExponentialBackoffRetry(1000, 5));
    client.start();

    LeaderLatch latch = new LeaderLatch(
        client, "/my-service/master-election", args[0]);
    latch.addListener(new LeaderLatchListener() {
      public void isLeader() {
        // Start only idempotent, fenced master work here.
        startMasterWork();
      }
      public void notLeader() {
        stopMasterWork();
      }
    });
    latch.start();

    Runtime.getRuntime().addShutdownHook(new Thread(() -> {
      closeQuietly(latch);
      closeQuietly(client);
    }));
  }
}
Production noteLeader election alone does not stop a paused old master from resuming. Protect the downstream resource with a monotonically increasing fencing token or another idempotency mechanism.
07 / PITFALLS

The interview answers that show depth

Most ZooKeeper mistakes come from confusing liveness with safety or confusing a notification with the state itself.

✓ Treat watches as hints

On notification, read the state again and install the next watch. Watches are one-shot.

✓ Wait for session expiration

A TCP blip does not immediately remove ephemeral nodes; they vanish after the negotiated session timeout.

✓ Make master work idempotent and fenced

Failover can overlap with a slow or partitioned prior master.

✕ Do not use ZooKeeper as a database

It is optimized for small coordination state and high read ratios, not large objects or streaming writes.

In a 5-node ensemble, how many failures can you tolerate?

2. Quorum is 3, so 3 servers must remain alive.

Who handles an app write sent to a ZooKeeper follower?

The follower forwards it; the leader orders the proposal.

What makes an app candidate disappear automatically?

The ephemeral znode is tied to its ZooKeeper session.

Why watch only your predecessor?

Only the next eligible candidate needs to wake up.
