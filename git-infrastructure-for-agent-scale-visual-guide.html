When every agent becomes a Git power user

Agentic development turns a repository from a mostly human-paced archive into a hot, concurrent system. GitHub’s response is a classic distributed-systems move: coordinate less, and separate durable storage from elastic compute.

The central tension: the current design uses the same full replicas for durability and read scale. More read capacity therefore adds work to every write. The new direction splits those jobs.

01 / THE PRESSURE

Human-scale latency becomes agent-scale throughput.

A person may push a few times per hour. An agent can checkpoint after nearly every action, while CI and scanning fan each push out into many reads. Small per-operation costs now sit inside tight loops.

06 / SYSTEM DESIGN TAKEAWAYS

The reusable ideas behind the Git story.

These patterns travel well beyond Git—to databases, model serving, build systems, and any workload where hot compute is accidentally carrying durable responsibility.

01

Separate scaling axes

If reads and writes scale for different reasons, avoid making them buy the same resource.

02

Find the true serialization point

For a Git push, immutable object work can spread out; the ref update is the small contested decision.

03

Move housekeeping away from traffic

Compaction and garbage collection should not steal CPU or I/O from live requests.

04

Design failure domains deliberately

A serving worker’s failure should reduce temporary capacity, not threaten the authoritative copy.

05

Preserve semantics while changing mechanics

Branch protection, review, audit, visibility, and human control remain constraints—not optional extras.

06

Optimize for the tight loop

Agent workflows amplify push latency, merge contention, and read fan-out that humans might barely notice.
