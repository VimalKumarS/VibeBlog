Chapter 1

The system is speaking.
Can you hear it?

Every service in a distributed system produces thousands of metric samples per second. Most are normal. A few are not. The question is: which ones?

Traditional monitoring uses static thresholds — fire an alert when CPU > 80%. But modern AI/ML systems are dynamic. A p99 latency of 800ms might be perfectly normal during batch inference and catastrophically bad during real-time serving. Static thresholds generate noise and miss real anomalies.

Static threshold
CPU alert at 80%.
Fires during every scheduled batch job.
Engineers learn to ignore it.
When a real anomaly fires — nobody looks.
Anomaly detection
Learns that CPU spikes at 02:00 are normal.
Detects that the same spike at 14:00 on a Tuesday is unusual.
Fires fewer, higher-fidelity alerts.

Chapter 2

Three signals. One truth.

OpenTelemetry unifies metrics, traces, and logs under one collection model. Anomaly detection operates on all three — and the magic happens when they're linked.

📊

Metrics

What is happening right now? Counters, gauges, histograms. The anomaly detector's primary input. p99 latency, error rate, request throughput.

🔗

Traces

Where did the time go? A tree of spans, each a unit of work. The anomaly's root cause lives here — the specific span that took 4 seconds.

📋

Logs

What was said at that moment? Structured logs carry trace_id — linking the narrative of a request to its timing and its anomaly score.

Chapter 3

The Collector is the brain.

Before any anomaly model sees a metric, the OTel Collector pre-processes it: normalises URL paths, scrubs high-cardinality labels, drops noise, and routes to the right backend.

collector processor chain — watch data transform stage by stage stage: receiver
Cardinality rule: user_id, request_id, and raw URL paths must be normalised or dropped in the Collector before reaching Prometheus. 1M unique user_ids = 1M time series = OOM crash.
# The critical transform processor — URL normalisation + label scrubbing transform/scrub_metrics: metric_statements: - context: datapoint statements: - 'replace_pattern(attributes["http.target"], "\\?.*$", "")' - 'replace_pattern(attributes["http.target"], "/[0-9]+", "/{id}")' - 'delete_matching_keys(attributes, ".*_id$")'
Chapter 4

How the algorithm
finds the strange.

Isolation Forest is the workhorse of cloud-native anomaly detection. It isolates anomalies rather than profiling normality — and it works on day one, with no historical data.

isolation forest — interactive demo: click to add data points 0 points
Insight: Anomalous points are isolated with fewer splits (shorter paths). Normal points need many splits — they're packed together. The anomaly score = average normalised path length across all trees.
Score < 0.5 → likely normal · Score > 0.6 → anomalous · Score > 0.75 → high confidence anomaly

Three unsupervised algorithms — when to use each

🌲

Isolation Forest

Best for general-purpose metric anomalies. Works on any dimensionality. No history needed. Apple Kruthika's KubeCon EU 2025 recommended model.

🔄

Autoencoder

Best for multivariate, correlated signals. High reconstruction error = anomaly. Needs mild warm-up (100+ samples). Good for ML pipeline feature drift.

📏

Dynamic threshold (3σ)

Best for single-metric, high-frequency signals. Compute rolling mean ± 3 standard deviations. Instant, lightweight, interpretable. Replaces static rules.

Chapter 5

The cold-start paradox.
Solved.

Traditional ML anomaly detection requires weeks of historical data to build a baseline. But you need detection most on day one — when the system is newest, most fragile, and most likely to fail.

detection coverage over time — traditional vs pre-trained approach
anomaly_score(x) = 2−E[h(x)] / c(n)
h(x) = average isolation path length for point x across all trees
c(n) = expected path length for a dataset of size n (normalisation constant)
Key: this formula works on any input distribution — no historical baseline required.

Kruthika's insight (KubeCon EU 2025): Pre-trained models trained on generic cloud-native metric distributions generalise surprisingly well. The isolation forest doesn't need to know your app — it knows what "normal metrics" look like in general across Kubernetes workloads.
Chapter 6

From alert to root cause
in one click.

An exemplar is a pointer. When a metric histogram records an anomalously slow observation, it attaches the current trace_id as an exemplar. That trace_id is the smoking gun.

exemplar flow — click the orange dot to trace the anomaly to root cause click the spike

MTTR decomposition — where the time goes without vs with exemplars

MTTR = MTTD + MTTA + MTTR. Anomaly detection attacks MTTD (detect in <2 min). Exemplars attack MTTA (analyse in <5 min instead of 30). Auto-remediation attacks MTTR (restart pod in <1 min). All three legs simultaneously.

The complete architecture: how anomaly detection scales across a production fleet using consistent hashing, two-tier Collector deployment, and tail sampling that keeps every error trace.

consistent hash ring — trace routing across gateway fleet 6 gateways active
back-of-envelope: 50k req/s sizing

500k spans/sec

50k req/s × 10 spans/trace. Spread across 10 gateway instances = 50k spans/sec per instance.

1 GB RAM/instance

50k in-flight traces × 20 KB/trace = 1 GB trace buffer. 8 GB nodes, memory_limiter at 6 GB.

4 vCPU/instance

2 cores for span processing + 2 cores for tail sampling decision overhead. Scale on memory, not CPU.

100% error coverage

Tail sampling policy: keep all ERROR spans, keep all traces >2s, keep 1% of nominal. ~2% overall rate.

Key insight: Use a headless Kubernetes service (clusterIP: None) for the DNS resolver, not a regular ClusterIP. kube-proxy round-robins before the Load Balancing Exporter can hash — defeating consistent routing entirely.
