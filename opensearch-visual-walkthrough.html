Chapter 1

What OpenSearch is
and why it exists.

OpenSearch is a community-driven, open-source search and analytics engine forked from Elasticsearch 7.10 in 2021. It stores, searches, and aggregates large volumes of semi-structured data — logs, metrics, documents, vectors — at millisecond speeds.

At its core, OpenSearch is a distributed document store with a powerful inverted index. Think of it as a search engine you can run yourself: you PUT documents in, you GET them back by searching field values, full text, or vector similarity — across billions of documents in under 100ms.

opensearch vs a relational database — why it's different showing: search query
📄

Document store

Stores JSON documents. Each document is a record. Documents live in an index (like a table). Fields are typed: keyword, text, date, integer, dense_vector.

🔍

Inverted index

Every text field is tokenised and stored inverted: term → [doc1, doc5, doc9]. This is what makes full-text search across billions of docs take under 10ms.

📊

Aggregation engine

Compute metrics (sum, avg, percentiles), buckets (date_histogram, terms), and pipelines in one query. Like SQL GROUP BY but distributed and on arbitrary JSON.

🧠

k-NN vector search

Store dense vectors (embeddings) alongside documents. Search by cosine or L2 similarity. Powers semantic search, recommendation, anomaly detection.

OpenSearch vs Elasticsearch: OpenSearch is a fork of ES 7.10 with the same REST API. If you know ES, you know OpenSearch. Key differences: Apache 2.0 licence, Security plugin free (was commercial in ES), ML Commons built in.
OpenSearch vs relational DB: No joins. No ACID transactions. But: 1000× faster full-text search, horizontal scaling to petabytes, native time-series aggregations, vector search.
Chapter 2

The cluster —
nodes, roles, and state.

An OpenSearch cluster is a group of nodes. Each node plays one or more roles. The cluster manager (formerly master) orchestrates them all. Understanding node roles is the foundation of everything else.

cluster architecture — click any node to explore its role 6-node LogFlow cluster
👑

Cluster Manager

Maintains cluster state: which indices exist, how many shards, which node holds which shard, node membership. Elected via Raft. 3 or 5 dedicated manager-eligible nodes for HA.

💾

Data Node

Stores shard data. Does indexing and search. CPU and memory intensive. Scale these horizontally for throughput. Keep heap at 50% of RAM, max 32GB (compressed OOPs limit).

🚦

Coordinating Node

Routes requests, fans out to shards, merges results. Stateless. Put a load balancer in front. All nodes are coordinating by default — dedicated ones for high-query clusters.

📥

Ingest Node

Runs ingest pipelines before indexing: parse, enrich, transform documents. Like Logstash but built-in. LogFlow uses ingest to parse log timestamps and add geo-IP fields.

cluster state — watch shard assignment when a node fails steady state
Cluster state is a giant JSON blob maintained by the cluster manager and replicated to all nodes. It contains: index settings, mappings, shard routing, node membership. Changes to cluster state are serialised through the manager — it's the single source of truth.
Chapter 3

From JSON document
to inverted index.

When you index a document, OpenSearch tokenises every text field, builds an inverted index mapping each term to the documents containing it, and writes to a Lucene segment. Understanding this chain is what separates good from great search engineers.

The inverted index — interactive term lookup

Lucene segments — the write path

Write path

  • Document arrives → written to in-memory buffer + translog (WAL).
  • Refresh (1s default) — buffer flushed to a new Lucene segment. Now searchable.
  • Flush — translog committed to disk. Segment files persist. Safe from crash.
  • Merge — background process combines small segments into larger ones. Reclaims deleted doc space.

Tuning for LogFlow

  • refresh_interval: 30s — logs don't need 1s freshness. Reduces segment count, improves write throughput.
  • translog.durability: async — async fsync. Risk: up to 5s of data loss on crash. Worth it for log pipelines.
  • index.codec: best_compression — for cold log archives. 40-60% smaller. Slower reads.
lucene segment lifecycle — refresh, flush, merge documents: 0

Chapter 4

Query DSL —
how search works.

OpenSearch queries are JSON structures sent to the _search endpoint. They combine two concepts: query (which documents match?) and aggregation (what are the statistics?). Understanding relevance scoring and query types is essential.

Relevance scoring — BM25

BM25 scoring — how term frequency and doc length affect relevance score: –
Term freq (TF) 3
Doc length 100
Doc freq (DF) 100
BM25 = IDF × (TF · (k1+1)) / (TF + k1 · (1 − b + b · dl/avgdl))
IDF (inverse document frequency) — terms that appear in fewer documents get higher scores. "error" in 1000 of 1M docs scores higher than "the" in 999K docs.
TF saturation — BM25 saturates term frequency. The 10th occurrence of "error" contributes far less than the 1st. This prevents keyword stuffing from inflating scores.
b=0.75 — length normalisation. Shorter documents with the same term count score higher. A log message with "error" once scores higher than a 10,000-word doc with "error" once.

Chapter 6

Sharding and replication —
the hardest part.

Sharding is how OpenSearch distributes data across nodes. Get it wrong and you'll either under-utilise hardware or hit the "too many shards" problem. This chapter covers sizing, routing, and rebalancing.

shard routing — how a document finds its shard idle
Primary shards 3
shard = hash(routing_value) % number_of_primary_shards
routing_value defaults to document _id. This distributes documents evenly. Override with routing=tenant_id to ensure all docs for a tenant land on the same shard — faster per-tenant searches.
Critical: You cannot change the number of primary shards after index creation. Get this right upfront. Rule of thumb: target 10–50 GB per shard, max 200M docs per shard.

Shard sizing — LogFlow

  • Daily ingest: 50M logs × ~500 bytes avg = 25 GB/day
  • Target 30 GB/shard → 1 shard per day initially
  • But: rollover when size hits 50 GB → 2 shards/day at peak
  • 3 primary shards × 1 replica = 6 shards total per index
  • 30 days retention × 6 shards = 180 shards. Well within 1000-shard soft limit.

The too-many-shards problem

  • Each shard is a Lucene index: file handles, heap memory, segment overhead.
  • Rule: max 20 shards per GB of heap. 32GB heap = 640 shards max per node.
  • Symptom: cluster slowdown, high JVM GC, "circuit breaker" errors.
  • Fix: increase shard size (fewer, bigger shards), use ISM to delete old indices, force-merge old segments.

Chapter 7

Security — TLS, RBAC,
and field-level control.

OpenSearch Security (formerly Open Distro Security) provides TLS encryption, authentication, role-based access control, and document/field-level security — all free and built-in. This is a major differentiator from Elasticsearch.

security model — layers from TLS to field-level click a layer

RBAC components

  • Users — authenticate via LDAP, SAML, OpenID, or internal user database.
  • Roles — define permissions: which indices, which actions (read/write/admin), which fields.
  • Role mappings — map users or LDAP groups to roles.
  • Action groups — named sets of actions (e.g., "CRUD" = create+read+update+delete).

LogFlow RBAC — multi-tenant isolation

  • service-reader role: read logflow-* indices, filtered by {"term":{"service":"payment-service"}}.
  • ops-admin role: full access to all logflow-* indices, cluster health, ISM.
  • ml-reader role: read access + _search + ML inference endpoint.
  • Field-level: trace_id field excluded from service-reader role (PII isolation).

Chapter 8

ML Commons —
k-NN, anomaly detection,
and neural search.

OpenSearch ML Commons brings machine learning inside the search engine. k-NN vector search, anomaly detection on time series, and neural search (semantic + keyword hybrid) — all without an external ML system.

k-NN vector search — semantic similarity vs keyword match add vectors then search
How it works: Embed your log message with a model (e.g. sentence-transformers/all-MiniLM). Store the 768-dim vector in a knn_vector field. At search time, embed the query and find the k nearest neighbours using HNSW (Hierarchical Navigable Small World) graph.
Why it matters: Keyword search misses "connection refused" when you search "network failure". k-NN finds semantically similar logs even if they share no keywords.

HNSW — the index structure

  • Hierarchical Navigable Small World graph — like a skip list for vectors.
  • Build time: O(N log N). Query time: O(log N). Approximate — not exact.
  • Parameters: m (connectivity, 16–64), ef_construction (build quality, 128–512).
  • Higher m = better recall, more memory. Tune for your accuracy/speed target.

Anomaly Detection plugin

  • Random Cut Forest algorithm on time-series metrics.
  • Detector on LogFlow: error_rate per service, p99 latency.
  • Real-time: scores every data point, fires alert when score > threshold.
  • Integrates with Dashboards for visualisation and alerting.

Back-of-envelope sizing for LogFlow

Daily ingest50M docs × 500B avg = 25 GB raw. After compression: ~10 GB/day. With 1 replica: 20 GB/day stored.
Shards per index1 daily index, 3 primary + 3 replica = 6 shards. Target 10-20 GB/primary shard.
Heap sizing32 GB heap per data node (compressed OOPs limit). 6 data nodes = 192 GB total heap. Rule: max 20 shards/GB → 640 shards/node.
Retention30 days hot × 6 shards = 180 shards. 60 days warm × 3 shards (no replica) = 180 shards. Total: 360 shards. Comfortable.
Query latencyp99 full-text search: <100ms. k-NN with HNSW ef_search=256: <50ms at 10M vectors. Aggregation on 30 days: <3s.
The one-sentence mental model: OpenSearch is a distributed inverted-index engine — documents in, tokens mapped to posting lists, BM25 scored, sharded across nodes, replicated for availability, secured with RBAC, queried via JSON DSL, and increasingly ML-augmented with k-NN and anomaly detection.
