ShopFlow — a distributed e-commerce platform

Throughout this guide, we'll deploy ShopFlow: a microservice system with an API Gateway, Product Service, Order Service, Payment Service, Inventory Worker, and a PostgreSQL database. Every Kubernetes concept will be illustrated by deploying, scaling, securing, or debugging part of ShopFlow.

Chapter 1

Why does Kubernetes exist?

Before Kubernetes, scaling a service meant SSH-ing into machines, manually starting processes, and praying nothing crashed at 2 AM. Kubernetes automates everything you used to do by hand.

The core insight: containers are great at packaging, but terrible at self-managing. Kubernetes is the control system that decides where to run containers, how many, what happens when one dies, how they find each other, and how to roll out updates safely.

before vs after kubernetes — click to compare showing: manual ops
🔄

Self-healing

Pod crashes → K8s restarts it automatically. Node dies → pods rescheduled on healthy nodes. No manual intervention.

📈

Auto-scaling

HPA watches CPU/memory/custom metrics and adds or removes pod replicas without any human in the loop.

🚀

Rolling updates

Deploy a new version with zero downtime. Roll back in one command if it goes wrong. Canary and blue/green built in.

🔍

Service discovery

Services get stable DNS names inside the cluster. product-service.default.svc.cluster.local always resolves, regardless of which pods are behind it.

Chapter 2

The control plane
and the data plane.

A Kubernetes cluster has two kinds of machines: the control plane (the brain) and worker nodes (the muscle). They communicate constantly to converge the cluster toward the desired state you declared.

cluster architecture — live reconciliation loop reconciling…

Control plane components

  • kube-apiserver — the only entry point. All kubectl commands hit the API server. Validates + persists to etcd.
  • etcd — distributed key-value store. The source of truth for all cluster state. Lose this = lose the cluster.
  • kube-scheduler — watches for unscheduled pods and assigns them to nodes based on resources, affinity, taints.
  • kube-controller-manager — runs all controllers: Deployment, ReplicaSet, Node, Endpoint controllers.
  • cloud-controller-manager — talks to AWS/GCP/Azure to provision load balancers, disks, routes.

Worker node components

  • kubelet — the node agent. Watches the API server for pods assigned to this node, starts/stops containers via CRI.
  • kube-proxy — maintains iptables/IPVS rules for Service IP routing. Handles clusterIP, NodePort, LoadBalancer.
  • Container runtime — containerd or CRI-O. Actually runs the containers. Docker is no longer supported as CRI.
  • CNI plugin — sets up pod networking. Flannel, Calico, Cilium. Assigns pod IP from the pod CIDR range.
desired state → reconciliation loop → actual state
Every controller in Kubernetes runs the same pattern: watch for drift between desired state (what you declared) and actual state (what's running).
ShopFlow example: You declare 3 replicas of product-service. A node dies. Actual = 2. Controller creates a new pod to fix the drift.

Chapter 4

How pods find each other.

Every pod gets a unique IP. But pods are ephemeral — their IPs change. Services provide stable virtual IPs and DNS names that survive pod restarts, scaling, and rollouts.

network layers — trace a request from browser to pod step 1 of 5

Service types

  • ClusterIP — virtual IP inside cluster only. Default. product-service gets 10.96.x.x — only pods can reach it.
  • NodePort — exposes on a port (30000–32767) on every node's real IP. Good for dev/testing.
  • LoadBalancer — provisions a cloud LB (AWS ALB, GCP LB). External traffic entry point. Expensive.
  • ExternalName — CNAME alias to an external hostname. Good for pointing to managed services.

Ingress vs Service

  • Service — layer 4 (TCP). Routes by IP and port. One service = one load balancer.
  • Ingress — layer 7 (HTTP). Routes by host and path. One Ingress controller = many services. Path-based routing: /api/products → product-service, /api/orders → order-service.
  • Ingress controller — nginx, Traefik, AWS ALB Ingress Controller. Reads Ingress resources and configures the actual proxy.
  • Gateway API — next-gen replacement for Ingress. More expressive. HTTPRoute, TCPRoute.
# ShopFlow Ingress — routes by path to microservices apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: shopflow-ingress annotations: nginx.ingress.kubernetes.io/rewrite-target: / spec: rules: - host: shopflow.example.com http: paths: - path: /api/products pathType: Prefix backend: {service: {name: product-service, port: {number: 8080}}} - path: /api/orders pathType: Prefix backend: {service: {name: order-service, port: {number: 8080}}}

Chapter 5

Persistent state in an
ephemeral world.

Pods are ephemeral — when they die, their filesystem dies with them. PersistentVolumes give pods storage that outlives them. This is how the ShopFlow PostgreSQL database survives pod restarts.

storage layers — PV, PVC, StorageClass and dynamic provisioning
💾

PersistentVolume (PV)

The actual storage — an AWS EBS volume, GCP Persistent Disk, NFS share. Exists independently of any pod.

📋

PersistentVolumeClaim (PVC)

A request for storage. "I need 20Gi of ReadWriteOnce storage." K8s binds it to a matching PV automatically.

⚙️

StorageClass

Defines how PVs are provisioned dynamically. "gp3" on AWS, "standard" on GCP. Annotations set the default class.

📦

emptyDir

Temporary volume that lives as long as the pod. Shared between containers in the same pod. Good for caches, scratch space.

# ShopFlow PostgreSQL — StatefulSet with PVC template apiVersion: apps/v1 kind: StatefulSet metadata: {name: postgres, namespace: shopflow} spec: serviceName: postgres-headless replicas: 1 volumeClaimTemplates: - metadata: {name: pgdata} spec: accessModes: [ReadWriteOnce] storageClassName: gp3 resources: requests: {storage: 20Gi}
Access modes matter: ReadWriteOnce (RWO) — one node at a time. ReadOnlyMany (ROX) — many nodes read. ReadWriteMany (RWX) — many nodes read/write. Most cloud block storage is RWO only. For RWX you need NFS or EFS.
Chapter 6

Configuration without
rebuilding images.

Hard-coding config in container images is an anti-pattern. ConfigMaps and Secrets let you inject configuration at runtime — change a database URL without touching the image.

ConfigMap

  • Non-sensitive config: API endpoints, feature flags, log levels, environment-specific settings.
  • Mounted as environment variables or as files in a volume.
  • File mount is better for large configs — the pod sees live updates when the ConfigMap changes (with ~60s delay).
  • Max size: 1 MiB. For large configs use an external store (Vault, AWS SSM).

Secret

  • Base64-encoded (NOT encrypted) by default. Enable etcd encryption-at-rest for real security.
  • Types: Opaque (generic), kubernetes.io/tls (TLS cert+key), kubernetes.io/dockerconfigjson (registry auth).
  • Never check Secrets into Git. Use External Secrets Operator to sync from Vault/AWS Secrets Manager.
  • RBAC restricts which ServiceAccounts can read which Secrets.
# ShopFlow — database config injected at runtime apiVersion: v1 kind: ConfigMap metadata: {name: order-service-config} data: DB_HOST: postgres.shopflow.svc.cluster.local DB_PORT: "5432" LOG_LEVEL: info --- apiVersion: v1 kind: Secret type: Opaque metadata: {name: order-service-secrets} stringData: # K8s base64-encodes automatically DB_PASSWORD: s3cur3p@ss STRIPE_API_KEY: sk_live_xxxx
configmap and secret injection — two patterns: env vars vs volume mount
Chapter 7

The scheduler decides.
HPA acts.

The scheduler places pods on nodes using a two-phase algorithm: feasibility filtering (which nodes can run this pod?) then scoring (which node is best?). HPA watches metrics and changes replica counts automatically.

HPA in action — CPU rises, replicas scale out replicas: 2 · CPU: low
HPA target CPU% 50%

Scheduler filters (feasibility)

  • ResourceFit — does the node have enough CPU/memory for the pod's requests?
  • NodeSelector — does the node have the required labels?
  • Taints & Tolerations — is the pod tolerated by the node's taints?
  • Affinity rules — required pod/node affinity constraints.
  • PodTopologySpread — is spreading this pod across zones required?

HPA formula

desiredReplicas = ceil(currentReplicas × (currentMetric / desiredMetric))
Example: 2 replicas × (80% CPU / 50% target) = ceil(3.2) = 4 replicas
  • Scale-up is fast (15s evaluation window).
  • Scale-down is slow (5 min cooldown by default) — prevents thrashing.
  • KEDA extends HPA with custom metrics: queue depth, Kafka lag, Redis list length.
# ShopFlow — product-service scales on CPU + custom request rate apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: {name: product-service-hpa} spec: scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: product-service} minReplicas: 2 maxReplicas: 20 metrics: - type: Resource resource: {name: cpu, target: {type: Utilization, averageUtilization: 50}} - type: Pods pods: {metric: {name: http_requests_per_second}, target: {type: AverageValue, averageValue: 1000}}

Chapter 9

Day-2 operations —
RBAC, Helm, and GitOps.

Getting a cluster running is day 1. Day 2 is everything after: access control, packaging, continuous delivery, observability, and cost management at scale.

RBAC model — who can do what to which resources explore the model

Helm

  • Package manager for K8s. A Chart = templates + values.yaml + metadata.
  • helm install shopflow ./charts/shopflow --values prod-values.yaml
  • One command deploys all 6 ShopFlow services with correct environment config.
  • Helm hooks: pre-install (run DB migrations), post-upgrade (smoke test), pre-rollback.

GitOps with ArgoCD/Flux

  • Git is the source of truth. The cluster must match what's in Git — always.
  • ArgoCD watches the Git repo and applies diffs automatically.
  • Deployment = merge to main → ArgoCD detects change → applies to cluster → health check.
  • Rollback = revert the Git commit → ArgoCD re-applies old state.
GitOps delivery pipeline — code to production idle
🔐

Network Policies

Default-deny all ingress. Allow only: order-service → postgres. payment-service → stripe.com. Nothing else connects to postgres.

💰

Resource Quotas

Per-namespace CPU/memory limits. shopflow-prod: max 100 vCPU, 200Gi. Prevents one team from starving others on shared clusters.

❤️

Probes

livenessProbe restarts stuck pods. readinessProbe removes unhealthy pods from Service endpoints. startupProbe protects slow-starting apps from false liveness kills.

🚨

PodDisruptionBudget

minAvailable: 2 on product-service. Node drains during upgrades won't take it below 2 healthy replicas. Zero-downtime maintenance.

The K8s mental model in one sentence: You declare desired state in YAML → controllers reconcile actual state toward desired → the scheduler places workloads → kubelet runs them → services route traffic → HPA scales them → RBAC controls who can touch what.
