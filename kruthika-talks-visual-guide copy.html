Core argument — why static thresholds fail

static threshold vs dynamic anomaly detection — toggle to compare showing: static
Metric variance 3
Kruthika's opening statement: "Static thresholds fail for dynamic metrics." A p99 of 400ms might be normal at 3am and catastrophic at noon. A threshold that catches the noon anomaly fires constantly overnight.
The fix: Learn what "normal" looks like for this metric, at this time of day, with this load. Then alert on deviation.

What algorithms does she use?

📊

Statistical (3σ / z-score)

Rolling mean ± 3 standard deviations. Works immediately on any metric. Best for smooth, low-noise signals. Lightweight, interpretable, zero training.

🌲

Isolation Forest

Isolates anomalies with fewer random splits. Works on any distribution, no labels. Anomaly score 0–1. High score = isolated = anomalous. Her primary ML model.

📈

Seasonal decomposition

Separates trend + seasonality + residual. Detects anomalies in the residual after removing known daily/weekly patterns. Essential for cyclical metrics.

Missing instrumentation detection — unique insight

The problem

  • A pod that crashes silently emits nothing. No metrics at all.
  • Traditional monitoring can't detect what it can't see — you get no alert because there's no signal to threshold.
  • This is the silent failure mode: the anomaly detector has nothing to score.

Kruthika's fix

  • Maintain an expected metric inventory — a registry of what each pod should emit.
  • Use PromQL absent() to fire when a series goes missing.
  • Treat "metric disappeared" as a high-severity anomaly, regardless of the last known value.
# PromQL: fire when a metric series goes absent ALERT MissingPodMetrics IF absent(container_cpu_usage_seconds_total{pod="product-service-*"}) == 1 FOR 2m LABELS {severity="critical"} ANNOTATIONS {summary="pod stopped emitting metrics — silent failure"}
Interview signal from Talk 1
"How do you handle the case where a pod crashes but emits no metrics?"
This is directly from her talk. Answer: PromQL absent() on the expected metric series, plus an expected-metric registry. Treat absence of signal as a first-class anomaly. Silent failures are the hardest to catch and the most dangerous.

What is an exemplar — the exact mechanism

exemplar drill-down — step through the correlation chain step 1 of 4

OTel SDK implementation — how exemplars are emitted

# Python — exemplar attaches automatically when an active span exists from opentelemetry import trace, metrics tracer = trace.get_tracer("product-service") meter = metrics.get_meter("product-service") request_duration = meter.create_histogram( name="http.server.duration", unit="ms" ) with tracer.start_as_current_span("handle_request") as span: # OTel SDK auto-attaches trace_id as exemplar to this measurement request_duration.record( duration_ms, {"http.method": "GET", "http.route": "/products/{id}"} ) # The exemplar stored in Prometheus looks like: # {trace_id="4f2a…", span_id="b1c2…"} duration_ms 4210 @1234567890

OTel Collector config for exemplars

  • Enable exemplar storage in Prometheus: --enable-feature=exemplar-storage
  • OTel Collector: enable exemplars in the Prometheus exporter.
  • Grafana: enable "Exemplars" toggle on any histogram panel.
  • Tempo as the trace backend — Grafana queries it by trace_id from the exemplar.

The MTTA impact

  • Without exemplars: Metric spike alert → search logs by time range → guess which request → find trace manually → 20–45 minutes.
  • With exemplars: Metric spike alert → click orange dot in Grafana → Tempo opens with the exact slow trace → 30 seconds.
  • MTTA improvement: ~40× faster root cause.

The cold-start paradox — visualised

detection coverage timeline — traditional vs pre-trained approach
The paradox: You need anomaly detection most on day one — when the system is newest and most fragile. Traditional ML requires weeks of training data first. You're blind exactly when you're most exposed.
Kruthika's thesis: Pre-trained unsupervised models generalise across cloud-native workloads. Deploy the pre-trained model on day one. Accumulate data. Fine-tune weekly. Accuracy improves continuously but you're never blind.

Why unsupervised? Why Isolation Forest?

isolation forest intuition — click "add cluster" then "add anomaly" 0 points
Key property: Isolation Forest needs no labels and no historical training. It learns the concept of "normal" from the current data distribution. Anomalies are points that are isolated with fewer splits — shorter average path length in random trees.
Score < 0.5 = normal · Score > 0.6 = suspicious · Score > 0.75 = anomaly

The 3-minute answer that wins the interview
"Walk me through how you'd build anomaly detection for a new service with no historical data, that must work from day one."
"I'd ship a pre-trained Isolation Forest alongside the application — pre-trained on generic Kubernetes metric distributions, so it generalises without knowing this app specifically. From the first request, Prometheus time series feed into the scoring engine and every metric window gets an anomaly_score from 0 to 1. That score gets exported back to Prometheus as a derived metric, so Grafana can overlay it on existing dashboards.

For root cause speed, I'd ensure every request histogram has OTel exemplars enabled. When the anomaly_score spikes and fires an alert, the Grafana exemplar on the triggering histogram links directly to the exact trace in Tempo — MTTA goes from 30 minutes to under a minute.

Meanwhile, every normally-scored window accumulates as training data. A Kubeflow pipeline runs weekly: fine-tune the Isolation Forest on app-specific patterns, run it in shadow mode for 24 hours against production traffic, and promote if precision improves. By week 4, the model knows this app deeply. You were never blind — you just got smarter over time."
